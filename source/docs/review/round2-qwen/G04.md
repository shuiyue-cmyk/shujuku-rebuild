### G04-01 [P2｜已坐实] 批量写入的落盘前复核缺消息对象身份校验：校验让步窗口内删楼后，旧候选帧被写进错位楼层并覆盖该楼层原帧，随后严格落盘
- 位置：
  - `source/src/service/table/storage-frame-v2-persist.ts:3114-3121`（批量路径新复核，只查 `!chat[index] || chat[index].is_user`）
  - 对照单写路径 `source/src/service/table/storage-frame-v2-persist.ts:2765-2772`（多一条 `chat[target.index] !== target.message` 对象身份校验）
  - 候选构造 `source/src/service/table/storage-frame-v2-persist.ts:2983-2992`（`chat.slice()` + 目标消息浅拷贝）、落盘 `3128-3145`
- 触发：用户在可视化编辑器改行后点保存（`visualizer-data-ops.ts:439` → `persistTableMutationLogBatchV2_ACU`，target 是各表 `getLatestV2SheetReplayMessageIndex_ACU`，常为聊天中段楼层）。批量核心先跑收敛校验回放（2957-2963，带 `yieldBudgetMs: 8`，大表时按帧/条目边界反复 `setTimeout(0)` 让出主线程，窗口可达数百毫秒以上），再跑写时严格探针（3095-3103）。窗口内用户在聊天里删除目标楼层之前的任意一条消息（MESSAGE_DELETED 由宿主同步 splice，同一数组引用、chatId 不变）。
- 现象：楼层整体前移一位后，`chat[index]` 是另一条 AI 消息，复核 `!chat[index] || chat[index].is_user` 通过；随后 `chat[index].TavernDB_ACU_IsolatedData = candidateChat[index].TavernDB_ACU_IsolatedData` 把「按旧楼层消息构造的候选帧（旧帧 + 本次 entry）」整份写进错位消息，覆盖它自己的帧（其原有 logEntries / checkpoint 丢失），再 `saveChatToHostStrict_ACU()` 落盘。结果：同一份帧内容出现在相邻两楼（重复 entryId / 可能双根），被覆盖楼层的历史帧永久丢失，后续回放高概率进入兼容只读态。切聊场景（本次提交新加的守卫目标）能拦住，删楼错位场景拦不住。
- 原因：复核只做「数组引用 + chatId + 目标存在且非 user」，没有像单写路径那样比对目标消息对象身份：
  ```ts
  // persist 3114-3121（批量）
  if (getChatArray_ACU() !== chat || getActiveChatStorageIdentity_ACU(chat) !== preparationChatIdentity) {
    throw new Error('目标聊天已切换，已拒绝旧的批量表格保存。');
  }
  for (const index of targetByIndex.keys()) {
    if (!chat[index] || chat[index].is_user) throw new Error('批量保存目标已变化，已拒绝旧结果。');
  }
  // 对照单写 2769：if (chat[target.index] !== target.message || target.message.is_user) throw ...
  ```
- 已排除：
  - `transactionContext.assertFresh`（table-write-transaction.ts:467-520）只比对 runtime revision（表格写入版本），删楼是宿主行为，不推进 revision，拦不住。
  - 新增的 `abortTableFillRequestsWithStaleTarget_ACU` 只中止在途 AI 填表请求（watch 登记在 `collectGroupFillResponse_ACU`），可视化保存不走该登记。
  - 调用方 `assertVisualizerContextMatches_ACU(expectedContextKey)` 只校验聊天身份（chatId+isolation），且在批量核心自身的校验回放**之前**执行，覆盖不到这段窗口。
  - 批量核心内两次校验回放都传了 `yieldBudgetMs`（2963、经由 validateAppendedOperationsReplayCandidate 的 696），窗口是本次提交刻意引入让步后真实存在的；单写路径同一提交里补了对象身份校验，批量路径漏了。
- 测试：`tests/service/table/storage-frame-v2-persist.test.ts:5484-5530`（「保存回放期间切换聊天」it.each single/batch）只模拟了 chatIdentity 变化（切聊），没有模拟「同一聊天内 splice 删楼导致目标索引错位」；`grep 批量保存目标已变化 tests/` 无命中，即新复核的两条 throw 都没有直接用例，错位分支完全未覆盖。
- 修法方向：批量核心在构造候选时按 index 记下当时的 live 消息对象引用，落盘前复核改为 `chat[index] !== 记录的对象` 即 throw（与单写路径同口径）；顺带把 `latestCheckpoint.index`（convergence 根帧）也纳入身份复核。
- 与上一轮复审的关系：新问题（361dab07 新增守卫自身不完整；不属于 R2B 任何一条的回归）。

### G04-03 [P2｜待坐实] runtime-only flush 的 T0 快路径在提交锁外清登记：与并发 skipChatSave 外部写入互不互斥，窗口内对同一张表的新写入登记被误清，脚本写入滞留运行时、重载后丢失
- 位置：
  - `source/src/service/table/runtime-only-pending-flush.ts:112`（锁外读 pending）、`116-124`（锁外读运行时快照 S0）、`145-152`（异步回放比对）、`153-158`（T0 快路径：diverged 为空即 `clearRuntimeOnlyPendingSheetKeys_ACU(scope, candidateSheetKeys, ...)`，全程不持提交锁）
  - 对照持锁路径的同文件 `214-233`（注释明确声称「mark 同样只在提交锁内发生，清账与并发 mark 互斥」——该主张只对事务内清账成立，对 T0 清账不成立）
  - mark 侧：`source/src/service/table/table-update-commit.ts:477`（skipChatSave 提交在 `runCommit` 持锁内 `markRuntimeOnlyPendingAfterSkipChatSave_ACU`）→ `runtime-only-pending-state.ts:77-98`
- 触发：前置条件是某表 A 已有登记但运行时内容与聊天回放一致（「陈旧登记」：例如脚本先做了一次内容无变化的 skipSave 写入，或 A 的变更已被某次不经过 flush 的普通提交顺带物化进聊天——模板提交、恢复、迁移等路径不清登记）。此时任一 flush 触发点（生成前 seed flush `init.ts:246`、填表前 `update-orchestrator.ts:1099`、普通提交前 `table-update-commit.ts:248`）进入 T0；在 S0 快照之后、T0 清账之前，外部脚本经开放 API 对 A 做 skipSave 写入并在持锁提交里重新 mark A。
- 现象：T0 比对用的是 S0（写者改动之前）→ A 与回放一致 → diverged 为空 → 走 156 行清账，把 A 的登记（含写者刚 mark 的那次）连同 deletedSheetKeys tombstone 一起清掉；flush 返回 `flushed:false` 且不进事务，写者的运行时改动从此没有登记 → 永远不会被物化进聊天帧：AI 填表基底看不到这些行（重复 INSERT / UNIQUE 冲突，正是本模块要防的事故），聊天重载后行直接消失；tombstone 被清则已删除的表在下次回放中复活。
- 原因：登记清除与登记写入不在同一把锁下，且清账依据的是窗口前的 T0 快照：
  ```ts
  // runtime-only-pending-flush.ts:153-158（锁外）
  if (divergedSheetKeys.length === 0 && !requiresFullSnapshot) {
    clearRuntimeOnlyPendingSheetKeys_ACU(scope, candidateSheetKeys, { dropAllFlag: pending.all });
    return { flushed: false, sheetKeys: [] };
  }
  ```
- 已排除：持锁重算路径（171-264）无此问题——事务内重读 pending、重取 fresh 快照、按 fresh 集清账，且失败路径补登记（274-277）；`clearRuntimeOnlyPendingSheetKeys_ACU` 的按键清除对「窗口内新登记的其它表」是安全的（不在 T0 候选集内），漏洞仅限「T0 候选集内的表被并发写者再次改动+登记」；`markRuntimeOnlyPendingAfterSkipChatSave_ACU` 恒置 `all:false`（table-update-commit.ts:231-233），故 `dropAllFlag` 分支在生产中不可达，不影响本结论；外部写入在 AI 填表进行中被 `assertNoActiveFillForExternalMutation_ACU` 拒绝，但 T0 的多数触发点（seed flush、可视化保存前、模板提交前）不在填表态，拦不住。
- 测试：`tests/service/table/runtime-only-pending-flush.test.ts` 的并发用例（192、221、273、293、327 行）全部针对「持锁重算」路径的窗口；T0 快路径只有单线程用例（128 行「全部一致时清空登记且不提交」），没有「T0 窗口内并发写者 mark 同一表」的用例。
- 修法方向：T0 判定 diverged 为空时不要在锁外清账——要么直接返回且保留登记（交给下一次持锁重算清账，语义安全只多一次比对），要么把 T0 清账挪进提交锁内并复用持锁路径的 fresh 重算结果。
- 待坐实缺口：未用探针复现完整交错（需要 mock 提交锁 + 定时交错）；「陈旧登记」（pending 非空但运行时==聊天）的实际产生频率未量化，代码上确认模板提交/恢复/迁移等直接走 persist 的路径不清登记。
- 与上一轮复审的关系：新问题（上一轮 block2b 未覆盖本文件）。
