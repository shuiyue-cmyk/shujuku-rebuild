## 发现

### G03-01 [P1｜已坐实] `<if>` 嵌套解析用「第一个 `<else>`」切分支：内层 if 带 `<else>` 时，外层分支被切错——该保留的内容被丢弃、该隐藏的分支泄漏进提示词，原始模板标记也被原样发给模型

- 位置：
  - 根因：`source/src/service/runtime/template-vars/if-block-parser.ts:149-156`
  - 同文件 `:130` 已经在扫描时正确识别过「顶层 `<else>`」（`elseMatch && nestingLevel === 1`），但只用来推进游标，位置没被记下，`:149` 又用裸正则重新找了一遍
  - 受影响的调用方（都在本组范围外，但吃的是同一个解析器）：`source/src/service/ai/prompt-builder/prompt-api-call.ts:249`（**填表提示词**）、`source/src/service/runtime/helpers-remaining.ts:268`（宿主最终提示词里的**每一条消息**，含世界书内容）、`source/src/service/optimization/content-optimization.ts:243`（正文替换提示词）、`source/src/service/runtime/plot-runtime/plot-tag-utils.ts:95`（剧情推进世界书内容）
- 触发：`promptTemplateSettings.enabled` 默认为 `true`（`state-manager.ts:540-544`）。用户在填表提示词、世界书条目或剧情任务世界书里写「外层 `<if>` 的**成立分支**里再嵌一个带 `<else>` 的 `<if>`」——这是本模块自己文档承诺支持的形态（`if-block-parser.ts:36-38`「支持 else 和嵌套」、`service/template-assistant/reference-docs.ts:180`「递归解析嵌套 `<if>`」），且 `maxNestingDepth` 默认 10。
- 现象（探针 2 实测输出，`context.seedContent = '战斗'`）：

  | 模板 | 正确结果 | 实际结果 |
  |---|---|---|
  | `<if seed="战斗">OUTER_TRUE<if seed="战斗">INNER_TRUE<else>INNER_FALSE</if>TAIL<else>OUTER_FALSE</if>` | `OUTER_TRUEINNER_TRUETAIL` | `OUTER_TRUE<if seed="战斗">INNER_TRUE` |
  | 同上但外层条件不成立 | `OUTER_FALSE` | `INNER_FALSE</if>TAIL<else>OUTER_FALSE` |
  | 对照：内层不带 `<else>` | `OUTER_TRUEINNER_TRUETAIL` | 同正确值 ✅ |
  | 对照：`<if>` 写在外层 `<else>` 里 | `BCD` | 同正确值 ✅ |

  即：外层成立时 `TAIL` 及之后的全部内容被**静默丢弃**，且未闭合的 `<if seed="战斗">` 原文进了提示词；外层不成立时，本该被条件排除的 `INNER_FALSE`、`TAIL` 连同 `</if>`、`<else>`、`OUTER_FALSE` **全部**泄漏进提示词。
- 原因：`parseSingleIfBlock_ACU` 先用嵌套计数正确定位了配对的 `</if>`，拿到 `ifBody`，但切分成立/不成立两个分支时用的是全文第一个 `<else>`：
  ```ts
  const ifBody = content.slice(ifStartTagEnd, nearest.index);
  let ifContent, elseContent;
  const elseTagMatch = ifBody.match(/<else>/i);      // ← 不跟踪嵌套，命中的是内层 <else>
  if (elseTagMatch && elseTagMatch.index !== undefined) {
    ifContent = ifBody.slice(0, elseTagMatch.index);
    elseContent = ifBody.slice(elseTagMatch.index + elseTagMatch[0].length);
  }
  ```
  内层 `<else>` 位置更靠前，于是 `ifContent` 在内层 `<else>` 处被截断（丢掉 `INNER_FALSE</if>TAIL<else>OUTER_FALSE` 里属于外层成立分支的 `TAIL`），`elseContent` 则从内层 `<else>` 之后开始（把内层的 else 内容、内层 `</if>`、外层 `<else>` 之后的内容全都当成「外层的 else 分支」）。截断后的 `ifContent` 里 `<if>` 没有配对 `</if>`，递归解析时 `parseSingleIfBlock_ACU` 返回 `null`，`parseIfBlocksInContent_ACU:100-101` 就把原始 `<if ...>` 标签当普通文本原样输出。
- 已排除：
  - 不是「用户写错模板」：`<else>` 只在 `nestingLevel === 1` 时被扫描器当作外层的 else（`:130`），说明设计意图就是只认顶层 `<else>`；`:149` 的实现与该意图不一致。
  - 不是被上游归一化挡住：`prompt-api-call.ts:239-249` 的顺序是 `parseRandomTags → replaceRandomVariables → replaceDbSqlVariables → parseIfBlocksInContent`，没有任何一步会先把内层 `<else>` 消化掉；`helpers-remaining.ts:252-269` 同序。
  - 不是只在填表路径：`helpers-remaining.ts:270-286` 对宿主 `data.messages` 里**每条**消息（含历史 AI 回复、用户消息、世界书注入片段）都跑一遍 `processPromptTemplateContent_ACU`，所以世界书条目里写了这个形态同样会被切坏。
  - 递归深度守卫（`:44-48`）与本问题无关：命中深度上限时是把原文原样返回，而本缺陷在 depth=0 就能复现。
- 测试：`tests/service/runtime/template-vars/if-block-and-condition.test.ts`（10 个用例）只覆盖**平铺**的 `<if>…<else>…</if>`（`:102`、`:115`）与嵌套但内层不带 `<else>` 的形态；`tests/service/ai/prompt-api-call.test.ts`、`tests/service/runtime/helpers-remaining.test.ts`、`tests/integration/template-var-pipeline.test.ts` 里的 `<else>` 用例同样是平铺形态。没有任何用例把「内层带 `<else>` 的 `<if>` 放在外层成立分支里」，所以全绿。
- 修法方向：`parseSingleIfBlock_ACU` 的扫描循环里已经在 `nestingLevel === 1` 时识别到顶层 `<else>`（`:130`），把它的绝对位置记下来（例如 `topLevelElseIndex`），`:149-156` 改成按这个位置切 `ifBody`，找不到顶层 `<else>` 时才 `elseContent = ''`。修完补一个「外层成立 / 外层不成立 × 内层带 else」的红用例。
- 与上一轮复审的关系：**新问题**。`block3-chat-runtime-settings.md:12` 的「未覆盖」清单里明确列了 `template-vars 的 … if-block-parser.ts`，本轮是首次读穿。

  |---|---|---|
  | `人物表/张三 > 5` | true | **false** |
  | `人物表/张三/体力 > 5`（三段式） | true | true ✅ |

## 设计层面的疑虑（不计入缺陷）

1. **前台生成上下文 TTL 放到 30 分钟**（`state-manager.ts:56-63`、`:161-166`）。修 issue #2 的方向没错，但代价是：一旦某次前台生成的 ENDED 真的丢了，`hasActiveForegroundGeneration_ACU()` 会在最长 30 分钟内持续为真，`settings-ui-connect.ts:283-295` 的 `generation_in_progress` 会把这段时间内所有**非生成事件**触发的自动填表（MESSAGE_SWIPED / MESSAGE_DELETED 刷新、MVU_ANALYSIS_ENDED 重跑）静默丢弃，而此前 60 秒就自愈。缓解手段确实存在（下一次前台 STARTED 会在 `:179-183` 顶掉旧的未闭合上下文；GENERATION_STOPPED 会 `discardLatestGenerationContext_ACU`；切聊天会 `activeGenerations = []`，见 `injection-engine-state.ts:177` / `init.ts:321`），所以只在「ENDED 丢失且用户不再发新消息、也不切聊天」时才暴露。建议至少给 `generation_in_progress` 的跳过加一条用户可见的提示或计数，别完全静默。
2. **30 秒强制放开「正在填表」**（`state-manager.ts:665-672`）。这是刻意的防死锁取舍，但强制放开后旧轮仍在跑，而旧轮收尾时的 `_set_isAutoUpdatingCard_ACU(false)`（`update-orchestrator.ts:5992`、`:6088`，以及 `executeAutoUpdatePlan_ACU` 经 `setAutoUpdating(false)`）没有 `processUpdatesBatch_ACU:3946` 那种 `ownsAutoUpdatingFlag` 归属判定，会把新一轮刚拿到的标志一起放掉，重新打开 R2A-08 那类重叠填表窗口。建议把归属判定统一到调度层。
3. **`stoppedSendRetryChatKey_ACU` 没有 TTL、也不在标记时被消费**（`state-manager.ts:250-265`）。`clearStoppedSendRetry_ACU` 只在 `init.ts:1055-1057` 的「非 dryRun / 非 automatic_trigger / 非 quiet」生成里调用，所以中间夹着若干 quiet / dryRun 生成时标记会一直留着；用户之后对**另一条**消息点「重新生成」，`isRetryOfStoppedSend_ACU` 仍为真，会为它跑一次决策召回 + 剧情推进 + 纪要向量索引（`:272`、`:285`、`:293-304`），多出请求并改写本轮输入。建议加时间窗，或在「用户新发了一条消息」时就清掉。
4. **`refreshCommittedWorldbook_ACU` 把世界书刷新失败降级为告警**（`update-orchestrator.ts:362-372`）本身是上游 issue #34 的正确修法，但两条路径对「刷新失败后是否还做向量收尾」的处理不一致（统一路径跳过 `:2427`，legacy 路径照跑 `:3885-3894`）。目前无实害（向量 flush 按内容哈希增量，下一轮会补），但属于 R2A-11 点名的「重复实现漂移」的新一处，建议随跨组线索 1 一起收敛。

## 复核过但判定没问题的可疑点

（写下排除理由，避免核查者重复查证）

1. **目标楼层守卫会不会误杀正常填表？** 不会。`isSameReply_ACU`（`table-fill-target-guard.ts:46-50`）对同一消息对象只比 `swipe_id`，因此正文替换、MVU 追加变量块、宿主「继续」续写（都会原地改 `mes` / `send_date` / `gen_started`）不判失效；对象被换掉时才比 `[is_user, swipe_id, gen_started, send_date]` 指纹，因此消息对象被 JSON 往返重建（本库自己的 `chat-table-field-swap` 逐字段替换、`persistTablesToChatMessage_ACU` 落盘）也不判失效。8 个用例（`tests/service/table/table-fill-target-guard.test.ts`）把滑动、删楼重生成、前位删楼错位、原地改写、续写、隐藏楼/工具楼口径、JSON 往返、-1 目标都锁住了。
2. **共享 AbortController 会不会让一个组的目标失效连累同批其他组？** 不会。`abortTableFillRequestsWithStaleTarget_ACU`（`table-fill-target-watch.ts:30-45`）中止的是 watch 登记的 controller，而 bucket 的 key 就是 `${finalSaveTargetIndex}|…`（`update-orchestrator.ts:2632`），同一 bucket 内所有 job 的 `saveTargetIndex` 必然相同；bucket 之间串行（`:2676` 的 for + `await`），`unwatch?.()` 在 `finally` 里（`:1482-1484`）不会残留。legacy 并发路径（`update-scheduler.ts:375-409`）每个组各自走 `proceedWithCardUpdate_ACU`，controller 是各自 new 的（`presentation/triggers/update-process.ts:214`）；staging 与追平的 segment 也都是 `await` 串行。
3. **守卫在 `index >= snapshots.length` 时 fail-open（`table-fill-target-guard.ts:80-81`）会不会写到不存在的楼层？** 判为可接受。该分支只在「捕获的聊天比目标下标短」时命中：自动填表侧有 `cancelPendingAutoTasks_ACU`（`init.ts:1277`）+ 事件代次复检（`settings-ui-connect.ts:283-296`）在删楼后作废排队任务；追平侧在执行时重新规划（`orchestrateManualCatchUp_ACU`），且终态写入另有 `resolveSafeTerminalTargetMessageIndex`（`update-orchestrator.ts:4708-4711`）；落盘还有 `persistTableMutationLogV2_ACU` 自己的目标校验。没能构造出一条「守卫放行 + 落盘也放行 + 写到错楼层」的完整路径。
4. **`abortableDelay` 在 catch 块里 await，被中止时会不会抛出逃逸？** 不会。`shared/abortable-delay.ts:14-33` 明确「abort 则立即 resolve（不 reject）」，两处调用（`update-orchestrator.ts:1689`、`:3846`）之后都紧跟一次显式 `isStopped()` / `signal.aborted` 复检再返回 `aborted: true`。
5. **纠错历史会不会把请求越堆越长？** 不会。`retryHistory` 在 collect 内与 bucket 重试间累积（`:1582-1586`、`:1686`、`:3028`、`:3839`），但拼接时被 `withTableFillRetryHistory_ACU` 截到最近 2 轮（`service/ai/prompt-builder/table-fill-retry.ts:26`、`:57`），且只在本次请求内使用、不写表格不写聊天。
6. **`NameMapper.translateSql` 的列名替换是全局、不分表的（`template-vars/name-mapper.ts:400-410`），同一中文显示名在不同表映射到不同物理列名时会按 DDL 加载顺序选错列。** 探针 4 已坐实：`characters(owner TEXT -- 主人, nm TEXT -- 名字)` + `items(name TEXT -- 名字)`，`SELECT 名字 FROM characters` 在 items 先加载时翻译成 `SELECT name FROM characters`（返回「主人」列的数据，静默错值），在 characters 先加载时翻译成 `SELECT nm FROM items`（no such column，硬报错）。**判定为已知取舍，不报**：`service/template/template-import-validator.ts:87-145` 就是为此写的检测器（`display_column_translation_ambiguity` / `display_name_substring_hazard`，注释明写「These are warnings, not import blockers: they only break specific SQL shapes」），已在 `template-preset-service.ts:443` 接线；自动生成的模板用拼音 slug（`shared/sql-identifier-mapper.ts:76-81`），同一显示名在各表得到同一物理名，只在手写 DDL 或同表内拼音撞名加 `_2` 后缀时才分叉。（唯一遗留疑问见跨组线索 5：这些告警是否真的到了用户眼前。）
7. **目标守卫在提交阶段拒绝后会不会留下孤儿行？** 不会。守卫抛的是 `precondition`（`table-update-commit.ts:307-312`），`update-orchestrator.ts:3022-3026` 对非 `model` 直接 break、不再重试 AI；`table-update-commit.ts:413` 的「应用前」复检在 `apply()` 之前，`:427` 一旦 apply 成功就置 `requiresRuntimeReload`，`:444` 的「持久化前」复检失败会走 `:496-503` 的 reload / 按提交前快照恢复。R2A-03、R2A-04 的修复仍然成立。
8. **`failManualRefillSession`（`update-orchestrator.ts:5286-5292`）不回传 `postCommitWarnings`，已提交 bucket 的世界书告警会不会丢？** 判为无实害：该函数在返回前调用了 `refreshData()`（`:5282`），手动填表的 `refreshData` 是 `refreshMergedDataAndNotify_ACU`（`useManualUpdate.ts:552`），会重做一次世界书同步；且 UI 侧 `useManualUpdate.ts:572-579` 本来就只在成功分支拼告警文案，两边口径一致。
9. **`helpers-data-merge.ts:653-662` 的 `lastMergeWarnings` / `lastMergeQuarantinedSheetKeys` 只在「有 mergedData 且有可用 guide」的分支被刷新，另一条 return 路径不清空，会不会让下一个消费者读到上一次的陈旧告警？** 追不出可达路径：`refreshMergedDataAndNotify_ACU` 是「合并后紧随消费」的唯一常规消费者（消费即清空，`:543-556`），`loadOrCreateJsonTableFromChatHistory_ACU`（`table-service.ts:430`）虽然合并不消费，但它后面接的还是 refresh 链。属理论上的暂存槽泄漏，影响上限是一条陈旧的结构性告警文案，不报。
10. **`processUpdatesBatch_ACU:3976-3978` 用户终止时返回 `{success:false, error:'填表任务已由用户终止。'}` 而不带 `aborted:true`**，于是 legacy 路径会弹一个 error 级 toast（`update-process.ts:307-309`）、调度层把它计成「N 组失败」（`update-scheduler.ts:402-408`）。只是提示级别/措辞不准（用户主动终止被报成失败），不改数据、不影响 `settings-ui-trigger.ts:283` 的判重登记（那里另有 `!wasStoppedByUser_ACU` 兜底），按 2.5「不要报纯措辞」不单列。
11. **`table-write-transaction.ts` 的锁与 `assertFresh`**：`acquireTransactionLocks_ACU:403-432` 获取到一半失败时按逆序释放已拿到的锁；`runTableWriteTransaction_ACU:534-536` 与 `runCommit:524-526` 都在 `finally` 里释放；`guardChatSwitch:444-450`（R3-09 修复）在拿锁之后、执行之前复核聊天身份。没找到泄漏或跨聊天误执行的路径。

14. **`state-manager.ts:446-460` 的 `awaitingChatBaseline_ACU`**：10 秒窗口过期判定（`:446-448`）、无配对 ENDED 只立基线不放行（`:449-454`）、配对上下文到达即清标记（`:469`）三处闭合；`resetScriptStateForNewChat_ACU` 会同时清 `lastGeneration` / `generationSeq` / `activeGenerations`（`injection-engine-state.ts:175-177`），所以载入聊天时那条 ENDED 确实走「无配对」分支。没找到「新聊天首轮真实回复被当基线吞掉」的可达序列（真实回复有配对的 STARTED/ENDED，走 `:465-471`）。
