## 发现

### G02-01 [P2｜已坐实] 「测试连接」在途时切换预设/新建/放弃修改，迟到的测试结果仍写回页面，挂到不相干的预设下（张冠李戴），且在途请求不被中断
- 位置：`source/src/presentation-v3/parts/ApiPresetEditor.vue:448-458`（`testConnectionForActive`，:454 迟到赋值）；对照 :303-304（注释明确承诺"切换预设、新建或放弃修改时清掉，避免张冠李戴"）、:364、:373（三处清空）、:386-388 + :485（切换路径触发 `syncActiveDraft`）。
- 触发：API 页选中预设 beta → 点「测试连接」（最长 60 秒在途）→ 测试期间在预设下拉里切到 alpha（草稿不脏时无确认弹窗，直接切）→ 20 秒后 beta 的测试结果返回。
- 现象：探针复现——切换瞬间结果确实被清空（页面短暂无"连接成功"），但 beta 的迟到结果 resolve 后 `connectionResult.value` 被重新赋值，alpha 的表单下显示「连接成功（20.0 秒）：这是 beta 端点的回复」。用户据此以为 alpha 可连通。失败结果同理（alpha 下显示 beta 的 401 原因）。另外在途测试请求不会被 abort，切换后仍继续消耗额度。
- 原因：结果赋值没有代际令牌/中止联动，`await` 之后无条件写回：
  ```ts
  async function testConnectionForActive(): Promise<void> {
    if (connectionTesting.value) return;
    connectionTesting.value = true;
    connectionResult.value = null;
    try {
      const preset = apiPresetFromDraft(draft);
      connectionResult.value = await store.testConnectionForConfig(preset.apiConfig, …);
    } finally { connectionTesting.value = false; }
  }
  ```
  `syncActiveDraft`/`startCreateDraft` 只做 `connectionResult.value = null`，挡不住之后到达的赋值。
- 已排除：`connectionTesting` 只防重复点击（按钮 busy 禁用，`UbButton.vue:19`），不防迟到写回；`selectPreset`（:376-389）、`startCreateDraft`（:367-374）、`watch(activePresetName)`（:485，flush:'sync'）三条路径都只清空不作废在途请求；service 层 `testApiConnection_ACU`（api-call.ts:823-863）无外部 signal 入参，组件也没传。除切换预设外，「+ 新建」「放弃修改」两个入口同样命中（同一赋值语句，机制相同，探针验证的是切换预设变体）。
- 测试：`tests/presentation-v3/api-page.test.ts:132-147` 覆盖了测试连接的成功/失败展示，但 mock 的 `testApiConnection` 立即 resolve，没有"在途期间切换"的时序用例，故未拦住。
- 修法方向：进入测试时取一个代际号（或新建 AbortController 传给 service），赋值前比对当前代际/表单身份，不匹配则丢弃；切换/新建/放弃修改时使代际失效并 abort 在途请求。
- 与上一轮复审的关系：新问题（测试连接功能为 805a72cf 新增，上一轮无此代码）。

### G02-02 [P3｜已坐实] 展示用错误体脱敏不覆盖 `?key=`（Gemini 转接密钥恰以 query 参数发出）与裸 `sk-…` 回显形态；与 log-buffer、填表重试反馈的脱敏实现三份分叉、覆盖互有长短
- 位置：`source/src/service/ai/api-call.ts:274-284`（`sanitizeUpstreamErrorBodyForDisplay_ACU`）；消费点 :648-649、:695-696、:1024-1026（错误文本进 `AgentApiHttpError.message` → 测试连接结果 UI、剧情推进运行日志、toast）；对照 :581 注释「Gemini 以 x-goog-api-key 与 ?key= 发出」；分叉对照 `shared/log-buffer.ts`（`maskSensitiveText_ACU`→`normalizeLogArg_ACU`，覆盖裸 `sk-` 16+ 位形态）与 `service/table/update-orchestrator.ts:699-712`（`sanitizeRetryFeedback_ACU`，覆盖 `?api_key=` 等 query 形态并整段抹掉 URL）。
- 触发：预设填了密钥、经酒馆转接走 Gemini 协议（TT 把密钥放进上游 URL 的 `?key=`）；上游或中转代理把请求 URL / 密钥原文回显进错误体（部分中转站的 4xx/5xx 会带原始请求信息）→ 该文本经"测试连接"结果、运行日志、Debug 导出展示。
- 现象：探针 F1（复制 :275-279 的同一组正则跑真实形态字符串）——
  - `…/v1beta/models?key=AIzaSyD-REAL-LOOKING-SECRET-abcdef` → **原样通过，未脱敏**（三条正则分别只认 `authorization:` 头形态、`bearer/basic` 前缀形态、`api-key/cookie` 等键名形态，裸 `key=` 不在键名清单）；
  - `Incorrect API key provided: sk-abcdefghijklmnopqrstuvwxyz…` → **原样通过**（无引号键名、无 Bearer 前缀的裸 sk- 不匹配；log-buffer 的 `\bsk-[A-Za-z0-9_-]{16,}` 规则能挡，但测试连接结果 UI 直接插值 `connectionResult.error`，不经 log-buffer）。
- 原因：函数头注释（:270-273）明言目的就是防"上游错误体回显 API key 进日志/UI"，但形态清单漏了 query 参数与裸密钥两种；且同一目的在库内已有三份独立实现（本函数、log-buffer、sanitizeRetryFeedback），覆盖范围互不相同——sanitizeRetryFeedback 反而把整段 URL 抹掉，是本组该函数应对齐的最严口径。
- 已排除：Debug 快照（`__ACU_DEBUG_LAST_API_BODY__`）另有打码（:603-617），不受影响；直接发送的 Gemini 密钥走 `x-goog-api-key` 头不进 URL（direct-send.ts:336-337），`directUnreachableHint_ACU` 只回显 host（:367-371），这两处没问题；日志缓冲路径（logWarn/logError）会再过一遍 log-buffer 脱敏，能挡裸 sk- 但同样挡不住 `?key=`。
- 测试：`tests/service/ai/api-call.test.ts:153`「上游错误体进入 AgentApiHttpError 前脱敏敏感值并限长」只覆盖了 Authorization/x-api-key/Cookie 头形态，未含 query 与裸密钥形态。
- 修法方向：给 `sanitizeUpstreamErrorBodyForDisplay_ACU` 补 `[?&]key=`/`[?&]api_key=` 与裸 `sk-`/`AIza` 前缀规则，或统一收敛到一份共享脱敏实现（对齐 sanitizeRetryFeedback 的 URL 抹除口径）。
- 与上一轮复审的关系：新问题（该函数为 79aa8573/cbaba9ca 时期引入的展示脱敏，上一轮 fix1 只扩了 Debug 快照打码面）。实际泄漏以"上游回显 URL/密钥"为前提，属防御纵深缺口而非常见路径泄漏，故定 P3。

## 设计层面的疑虑（不计入缺陷）

1. **Gemini 协议的存量「关闭思考」在直接发送下静默失效**：`resolveReasoningControl_ACU`（api-call.ts:404-409）对 `gemini_generate_content` + `'false'` 只发 `reasoning_effort:false`；直发侧 `buildGeminiGenerateContent_ACU`（direct-send.ts:262-266）仅认字符串，探针 B1 证实 `false` 时 `generationConfig` 里没有任何 thinkingConfig——模型按默认强度思考，"关闭"承诺落空（转接侧交给 TT 处理，0519d820 提交只明确了 Claude/Responses/Go 兼容接口三种落地，未提 Gemini）。缓解因素：现行 UI 思考强度下拉（ApiPresetEditor.vue:253-262）没有「关闭」选项，`'false'` 只能来自存量预设/外部设置接口，可达面小；且该档位在 Gemini 上的正确落地字段（thinkingBudget:0）在两通道都未实现过。
2. **直发 openai_compat 流式恒带 `stream_options.include_usage`**（direct-send.ts:140，探针 B4 证实），而转接路径只在有 usage 订阅方时才注入（api-call.ts:479-481）——同一预设在两种发送方式下请求体不同，不支持该参数的严格端点会只在直发时报错；用户可用「排除主体参数」剔除，但界面未提示这一差异。
3. **思考强度下拉缺「关闭思考/跟随全局」选项**：存量 `reasoningEffort:'false'` 的预设在下拉里回显空白（无匹配项），保存时值仍被白名单保留（useApiPresetManagement.ts:115-117，无数据丢失），纯展示歧义。
4. **`redirect:'error'` 下，端点做 301/308 跳转（如 apex→www、补尾斜杠）会被直发报成「多半是跨域被拦」**（direct-send.ts:366-371、458-467），文案与真实原因可能不符；这是 SSRF 守卫的既定取舍（direct-send.ts:443 注释），仅提示文案可能误导。
