## 发现

### G06-01 [P1｜已坐实] 发送时合成的指令楼指纹缺宿主 persona `name`，生产环境下「宿主重发重试」全链路失效，自动重试链静默死亡并谎报原因

- 位置：
  - `source/src/service/continuation/host-generation-bridge.ts:157`（`send()` 用合成对象算指纹）
  - `source/src/service/continuation/host-retry-mode.ts:29-41`（`hostMessageFingerprint_ACU` 把 `name` 计入哈希）、`:43-51`（`hasInstructionAnchor_ACU` 用真实楼重算比对）、`:59-75`（`resolveHostRetryMode_ACU` 配不上即 null）
  - 受影响消费点：`host-generation-bridge.ts:472-476`（重发前判定）、`continuation-orchestrator.ts:585-589`（`retryFloorsIntact`/`promoteHostRetry`/`discardPending`）
- 触发：任意一轮续写正文生成失败——空正文（1b36a19f ① 新加的门）、缺循环标签、短于 `minGenerationTokens`、或用户在宿主里手动停止生成（`failHostTurnForStoppedGeneration` 转 retry_ready）——之后进入自动/手动重试。
- 现象：`send()` 在发送前持久化的 capture 里，指令楼指纹用 `{ is_user: true, mes: instruction }` 合成（`name` 缺失 → 按 `''` 入哈希）；而宿主经发送框创建的真实用户楼带 persona 名（`ChatMessage.name: string` 为宿主类型契约必填字段，`source/@types/iframe/exported.sillytavern.d.ts:4`；取值来自 `name1`，本仓库 `data/gateways/host-state-gateway.ts:19-23` 默认「用户」，全库测试夹具用户楼均带 `name:'用户'`）。于是 `hasInstructionAnchor_ACU` 恒 false → `resolveHostRetryMode_ACU` 恒 null：
  1. 桥的自动重试链：reject → retry_ready → `autoRetryHostGenerationIfReady_ACU`（`host-generation-bridge.ts:413-425`）先调 `retryCurrentTurn` 把任务持久化成 running（`continuation-orchestrator.ts:675`），随后 `retryHostGenerationInner_ACU` 在 `:472-476` 因 mode null 直接放弃 → **宿主 regenerate/generate 从未发生**，自动链到此静默死亡（叠加 G06-03 的悬置 running）。
  2. 会话流留痕文案为「放弃宿主重发：楼层已与发送时不一致（承载指令的用户楼或上一轮正文已被删除）」——楼层其实原封未动，**诊断是假的**，会把用户引向排查删楼。
  3. 用户点「继续」：`continueTask` 的 `retryFloorsIntact`（`continuation-orchestrator.ts:585`）同样恒 false → `discardPending` → 回 Agent 重新规划同一轮 → 多烧一整轮内部 AI 调用，且聊天里**多出一条重复的指令用户楼**（原本设计的宿主 regenerate 会复用原指令楼）。
  4. `failHostTurnForStoppedGeneration` 注释承诺的「用户可以直接重试当前轮次」（`continuation-orchestrator.ts:875-879`）在生产不可达。
- 原因（关键代码，`host-generation-bridge.ts:151-159`）：
  ```ts
  const capture: ContinuationHostGenerationCapture_ACU = {
    ...
    instructionIndex: Array.isArray(chat) ? chat.length : 0,
    instructionFingerprint: hostMessageFingerprint_ACU({ is_user: true, mes: prepared.instruction.instruction }),
    ...
  };
  ```
  合成对象没有（也无法在发送前知道）宿主将写入的 `name`；而比对侧 `host-retry-mode.ts:50` 用真实楼全字段重算：
  ```ts
  return record.is_user === true && hostMessageFingerprint_ACU(record) === capture.instructionFingerprint;
  ```
  注意 `retryHostGenerationInner_ACU` 重发成功后会用真实楼重新捕获指纹（`:487`），即链路上其它环节都按真实楼口径，唯独首次 `send()` 是合成口径——两份口径分叉。
- 已排除：
  - 不是 `mes` 差异问题（`name` 单独即足以破坏匹配；探针对照组证明除 `name` 外全链路可用）。
  - `boundaryFingerprint`/`isHostSendBoundaryIntact_ACU` 不受影响（两侧都取真实聊天）。
  - 查过 `instructionFingerprint` 全部读写点（`model.ts:442`、`continuation-store.ts:1236,1253` 只做字符串校验，无归一化补救）。
  - 生产 `name` 非空的依据：宿主类型契约（d.ts 必填 `name: string`）+ `host-state-gateway.ts` 的 `name1 || '用户'` + 本仓库其他模块测试夹具（`tests/service/agent/agent-decision-engine.test.ts:159` 等）均带 name。未真机验证 TT 实例，故按「探针坐实机制 + 仓库内证据坐实前提」定级。
- 测试：`tests/service/continuation/host-generation-bridge.test.ts:23-29` 的 `recordHostTurn` 桩**用真实末楼重算了 `instructionIndex/instructionFingerprint` 再写入 pending**，恰好把生产 `send()` 的合成口径替换成了正确口径；`tests/service/continuation/host-retry-mode.test.ts:15-18` 与 orchestrator 测试（`:93,602,703`）的楼层/指纹全部无 `name`。因此 43 + 全部相关测试通过，却没有一条覆盖「合成指纹 × 带 name 真实楼」的生产组合。
- 修法方向：`send()` 的指纹口径与消费侧统一——要么发送返回后（宿主已建楼）用真实楼补记一次 capture（类似 `retryHostGenerationInner_ACU:487` 的做法），要么 `hasInstructionAnchor_ACU` 对 `send()` 场景只比对 `is_user + mes`（`name` 不参与），要么合成时取 `getUserName_ACU()`。同时把测试桩改为忠实透传 capture，并补一条带 `name` 楼层的端到端重试用例。
- 与上一轮复审的关系：新问题（缺陷随 `106975fc`（v9.6.9，2026-09-25）引入指令楼锚点时诞生，早于本轮基线，但 block4 未覆盖该组合；`1b36a19f` 新增的空正文自动重试使其从「重试降级」升级为「整条自动链死亡 + 假诊断」）。

### G06-02 [P2｜已坐实] 生成期间切走聊天，迟到的 GENERATION_ENDED/STOPPED 无法归属也不清理桥内存认领；切回后任务冻结在「等待宿主正文」，本轮正文永不确认

- 位置：
  - `source/src/service/continuation/host-generation-bridge.ts:232-238`（`onGenerationEnded` 认领失败即 return，不清理非当前聊天的 `startedByChat`/`armedByChat`）、`:217-230`（`claimsGenerationEnded` 只读当前聊天）、`:326-337`（`onGenerationStopped` 同样只按当前聊天身份清理）、`:124-128`（`hasLiveClaim`）、`:130-145`（`invalidateStartedByChat` 注释自述：残留条目会让「宽松 STARTED 被存在性判定永久拒绝、宽松 ENDED 被陈旧序列号拒绝——该聊天的续写链永久 BUSY」，但只挂了 stopTask/abandonAndCreate/clearContinuationData 三个出口，见 `continuation-orchestrator.ts:972,1148,1484`，**切聊天没有出口**）
  - 后果落点：`service/continuation/continuation-runtime.ts:299`（残留认领使 read() 保持 running 视图）、`continuation-orchestrator.ts:570-573`（`continueTask` BUSY）、`:788`（`readPendingHostTurn` 跨聊天返回 null）
- 触发：续写指令已发送、宿主正在生成正文时，用户切到另一个聊天（多聊天用户常见操作）；原聊天的生成在后台完成（或中止），GENERATION_ENDED/STOPPED 到达时当前聊天已是 B。之后切回 A。
- 现象（探针 `probe-G06-stale-claim-after-chat-switch.test.ts` 复现）：
  1. ENDED 在 B 上到达：`readPendingHostTurn()` 因 pending 身份 ≠ 当前聊天返回 null → 不认领 → 提前 return，A 的 `startedByChat`（含已绑定 seq）与 `armedByChat` 原样残留。
  2. 切回 A：`hasLiveClaim(A)===true` → `runtime.read()` 返回持久 running 视图，界面显示「等待宿主正文」+ 停止按钮；`continueTask` 被 `:570-573` 判 BUSY。
  3. A 里已经写好的本轮正文**永远不会被确认**（不会再有归属它的 ENDED）；用户再生成/重生成，新 STARTED 被 `:201` 的存在性判定拒绝、新 ENDED 被陈旧绑定序列号拒绝（`:228-229`）。
  4. 唯一出路是点「停止」（stopTask → `invalidateHostClaim`）再「继续」：等待轮被 `stopEnvelope`/`discardPending` 清掉，Agent 重跑同一轮——聊天里已有那条未确认的正文楼，重跑会产生同轮第二条正文（主 Agent 可能借 `adjust_progress` 校准缓解，但不保证）。
- 原因：桥的认领/清理全部以「调用时刻的当前聊天」为键；跨聊天的迟到事件既不归属也不触发对应聊天的残留清理，而 `derivePausedContinuationEnvelopeAfterReload_ACU` 的重载恢复只覆盖「认领已丢失」的反方向（`continuation-store.ts:1576-1579`），覆盖不了「认领残留但生成已死」。
- 已排除：查了 `invalidateStartedByChat`/`hasLiveClaim`/`invalidateHostClaim` 全部调用点（仅上述三个编排器出口 + runtime 装配 + read 视图），确认没有 CHAT_CHANGED 钩子、没有 TTL；`onGenerationStopped` 的清理分支只删当前聊天键（`:335-336`）。宿主重载聊天（换 chat 数组对象）也不会触碰桥内存。
- 测试：`host-generation-bridge.test.ts` 有「切聊天后不认领」的用例（chatIdentity 切换后 readPendingHostTurn 返回 null），但没有断言残留认领的后续影响；编排器侧 BUSY 用例不含桥内存状态。
- 修法方向：给残留认领加出口——(a) ENDED/STOPPED 归属失败时，若能从事件或 pending 身份解析出所属聊天，顺带 `invalidateStartedByChat(该聊天)`；或 (b) `armedByChat/startedByChat` 加 TTL（同 `LOCAL_RETRY_CLAIM_TTL_MS` 思路）；或 (c) `hasLiveClaim` 叠加「宿主当前确有生成在飞」的实时校验。至少应在切回聊天且等待轮无法归属时走一次重载派生。
- 与上一轮复审的关系：新问题（block4 只核了「不会写进错误聊天」，未核「认领残留冻结本聊天」；早于基线存在，未被报告过）。

### G06-03 [P2｜已坐实] 自动重试链先把任务置回 running、再放弃宿主重发，放弃路径不回写状态：任务悬置在持久 running，手动路径的提示文案与实际状态相反

- 位置：
  - `source/src/service/continuation/host-generation-bridge.ts:422-424`（`autoRetryHostGenerationIfReady_ACU`：先 `retryCurrentTurn()` 后 `retryHostGeneration()`）、`:473-476`（mode null 放弃分支只记日志 return false，无任何状态回写；对比 `:493-496` record 之后的失败分支会 `pauseForHostResultFailure`）

  - `source/src/presentation-v2/composables/useContinuationRuntime.ts:194-196`（手动路径 `retryHostGeneration()` 返回 false 时弹「宿主重新生成不可用，智能续写已暂停。」——持久状态其实是 running，从未被暂停）
- 触发：任何进入自动重试的失败（空正文/坏标签/短正文）都会先走 `retryCurrentTurn`；随后只要 `retryHostGenerationInner_ACU` 的 mode 判定失败就命中——当前因 G06-01 是**必然**命中；即使修好 G06-01，「reject 落盘 retry_ready → 重试延迟窗口内用户删掉指令楼/正文楼」以及「`continueTask` 判完 `retryFloorsIntact` 到桥真正重发之间楼层被改」两个竞态窗口仍然可达。
- 现象：探针 case1 实测 calls = `["rejectFailed","retryCurrentTurn"]` 且 `retryGeneration` 未被调用后，持久信封停在 `status:'running'` + `pendingHostTurn:'retry_ready'`，没有任何在飞生成。派生视图（`store.read()`）显示 paused，用户点「继续」可恢复（discardPending → 重规划），但：会话流的放弃理由文案错误（见 G06-01）；`repairPendingMaterials` 因 `task.status !== 'paused'`（`continuation-orchestrator.ts:500`）被拒；`readAutoContinueState` 因持久 running 恒不合格——所有依赖持久状态的判定都在读一个假状态，直到下一次成功写入。
- 原因：「决定重试」（编排器置 running）与「能否重试」（桥判 mode）分属两步，且顺序颠倒：桥在 mode 判定通过前就让编排器提交了状态跃迁，判定失败后没有对称的失败回写。
- 已排除：查了 `retryHostGeneration` 的全部调用点（桥内自动链 `:424`、`run_ACU` 手动路径 `useContinuationRuntime.ts:194`、`autoContinueAfterTurn_ACU:379`）——三条都在 `retryCurrentTurn`/`continueTask` 提交 running 之后，放弃分支均无回写；`:493-496` 证明作者在 record 之后的分支考虑过回写，唯独 record 之前的放弃分支漏了。
- 测试：`host-generation-bridge.test.ts` 的放弃用例（如「楼层形状不符时拒绝重发」）都直接预置 pending，不经过 `retryCurrentTurn`，因此没有断言放弃后的任务状态；编排器 `retryCurrentTurn` 测试不联动桥。
- 修法方向：把 mode 判定提前到 `retryCurrentTurn` 之前（桥先探测 `resolveHostRetryMode_ACU`，不可重发就不置 running，直接 `pauseForHostResultFailure` 或保留 retry_ready + stopReason）；或放弃分支补一次 guarded 的暂停回写；`useContinuationRuntime.ts:196` 的文案随实际状态改写。

## 设计层面的疑虑（不计入缺陷）

1. **deadline 在「大纲待确认」期间到期会让该大纲永久无法确认**：`expireDeadline_ACU` 把任务落为 paused + `duration_reached`（不可恢复停止），而 `acceptOutline` 要求 `awaiting_outline_review`（`continuation-orchestrator.ts:440-441`）、`replanRemaining`/`applyOutlineOpWithinLease_ACU` 拒绝带 stopReason 的任务（`:1261`）——用户唯一的出口是放弃任务或一键清空，确认面板无声消失。属于「duration_reached 不可恢复」取舍（`model.ts:11-19` 注释）的边界延伸，建议至少给一条「延长时长并恢复待确认态」的出口。
