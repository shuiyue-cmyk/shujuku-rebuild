## 发现

### G10-01 [P2｜已坐实] query embedding「截短重试」在关键词把查询撑超长时发送的是与首次完全相同的输入：该场景下发送照旧被停，还多烧一次注定失败的请求

- 位置：`source/src/service/vector/summary-vector-index-runtime.ts:548-549`（300 字符常量与注释）、`:729-737`（重试块，关键在 `:733` 的守卫与 `:735` 的 shortQuery 构造）
- 触发：用户在向量页开启「AI 补充关键词」（`keywordGenerationEnabled`，默认关），且 embedding 模型输入上限较小（如 512 token——正是 cf314c2d 加这个重试要救的场景）。用户输入本身不长（≤300 字符），但关键词 AI 返回的关键词（最多 24 条、**每条长度无上限**，见 `:166-171`）把 `queryText = userInput + '\n关键词：' + keywords` 撑过 300 字符，向量接口按输入超长拒绝。
- 现象：首次 `embedQuery(queryText)` 抛错 → `queryText.length > 300` 通过守卫 → 构造 `shortQuery = [userInput.slice(0,300), keywords.join('，')]...`。因为 `userInput.length ≤ 300`，`slice` 是空操作，**shortQuery 与 queryText 逐字节相同**（探针①断言 `calls[1] === calls[0]` 通过）→ 第二次请求必然同样失败 → 外层 catch（`:742-746`）返回 `query_embedding_failed` → 发送层停发（init.ts:1109-1115）并弹「交火记忆召回失败」。结果：同一条消息每次发送都失败（关键词长度由 AI 决定，重发大概率复现），用户只能自己关掉关键词 AI 或换接口才能发出；日志却写着「截短查询后重试一次」，实际一个字都没截，排查会被误导。
- 原因：截短只作用于 `userInput`，没有覆盖关键词侧的超长；也没有「重试输入与首次相同时跳过重试」的守卫。关键代码：

  ```ts
  if (queryText.length <= EMBEDDING_QUERY_RETRY_MAX_CHARS_ACU || !isActive()) throw error;
  logWarn_ACU('[交火模式纪要索引] query embedding 失败，截短查询后重试一次:', error);
  const shortQuery = [userInput.slice(0, EMBEDDING_QUERY_RETRY_MAX_CHARS_ACU), keywords.join('，')]
      .filter(Boolean).join('\n关键词：');
  queryVector = await embedQuery(shortQuery);
  ```

- 已排除：查了 `data/gateways/vector-embedding-gateway.ts`——网关对 input 无任何客户端截断（grep `slice|truncat|maxLength` 只命中报错文本裁剪），原样上送；查了 `parseKeywords_ACU`（runtime.ts:149-172）——只限条数（24）不限单条长度；查了 `generateKeywords_ACU`（:174-191）——失败时返回空数组（此时 queryText=userInput，走的是既有「长 userInput」分支，行为正确）；对照探针②证实 userInput 超长分支的截短有效。别处没有对本路径的归一化或守卫。
- 测试：`source/tests/service/vector/summary-vector-index-runtime.test.ts:701-710`「长消息被向量模型拒绝（输入过长）：截短查询重试一次后照常召回」只覆盖 userInput 超长的分支，断言的是 `retryInput.length < longInput.length`；没有「关键词侧超长」的用例，也没有断言重试输入必须不同于首次输入，因此拦不住。
- 修法方向：按总预算截短整个查询（例如 `shortQuery = queryText.slice(0, N)`，或优先裁关键词、再裁 userInput）；至少在 `shortQuery === queryText` 时直接 throw，不发注定相同的第二次请求，并让日志与实际行为一致。
- 与上一轮复审的关系：新问题（cf314c2d 在基线之后引入的重试机制自身的边缘缺口，不属于 R5 系列）。

### G10-02 [P3｜已坐实] 行指纹「单一来源」模块是死代码，仓内实际存在两套互相矛盾的活公式：注释承诺与代码不符

- 位置：
  - `source/src/service/vector/summary-vector-row-fingerprint.ts:4-7`（注释：「所有行指纹必须经由这里计算，避免多处内联公式漂移」）、`:26-44`（`buildSummaryRowFingerprint_ACU`：含 `v2` 版本标签、用源文本**哈希**参与指纹）
  - `source/src/service/vector/summary-vector-index-archive-service.ts:371-391`（私有同名 `buildSummaryRowFingerprint_ACU`：注释自称「单一指纹公式」，公式为原文直拼、**无**版本标签；`:624-632` 的行复用比较用它）
  - `source/src/service/vector/summary-vector-index-storage-service.ts:614`（第三套内联公式：比 archive 版**多 rowOrder** 字段，作为落盘行缺 `sourceFingerprint` 时的兜底）
- 触发：不需要用户操作——这是静态结构问题。全仓 grep 证实：`summary-vector-row-fingerprint.ts` 导出的 `buildSummaryRowFingerprint_ACU` **零生产调用方**（只有 `SUMMARY_VECTOR_SOURCE_TEXT_VERSION_ACU` 被 mirror-writer 引用、`hashSummaryVectorSourceText_ACU` 被 archive-service 引用）；tests 下也没有任何文件引用该函数。
- 现象：两处「单一来源/单一公式」的注释互相矛盾且都不成立；三套公式并存。当前没有功能性损坏——我核对了全部比较点：archive-service:632 的 `existingFingerprint !== prepared.sourceFingerprint` 两侧都用 archive 私有公式（自洽）；storage-service:614 的兜底值只写进 legacy manifest 的 rowIndex，全仓没有任何等值比较消费它（grep `sourceFingerprint ===/!==` 仅命中 archive 那一处）；镜像 V2 主链路的内容变化判定走的是 `vectorSourceHash`（单一公式，`hashSummaryVectorSourceText_ACU`），与 sourceFingerprint 无关。但「单一来源」模块里带版本标签的设计（版本升级→全量 mismatch→自动重嵌）实际没有接线，未来任何人按注释信任该模块、或把三套公式之一「统一」到另一套时，会静默改变 legacy 行的复用判定。
- 原因：spv9.2/V2 镜像移植（114ca32a）新建了共享指纹模块，但 legacy 归档链的两处公式没有收编，共享版从此悬空。
- 已排除：确认 `hashSummaryVectorSourceText_ACU`（vectorSourceHash 口径）在 archive/mirror-writer/mirror-rebuild/runtime 各处一致使用，镜像链没有公式分叉；确认 storage-service:614 的值不会流入 archive 的比较（legacy state 行自带 sourceFingerprint 时优先用存量值，且该值本来就是 archive 公式产出）。
- 测试：`tests/service/vector/summary-vector-index-archive-service.test.ts` 等只按 legacy 链自身行为断言，没有跨模块公式一致性测试；死模块无测试（grep 为空）。
- 修法方向：三选一并让注释与现实一致——把 archive/storage 两处接到共享模块（legacy 写链已死，改公式无存量风险，比较两侧同时换即可）；或删掉共享模块的死函数、修正其头注释；或至少在两处私有公式旁注明「与 row-fingerprint 模块公式不同、仅 legacy 链内自洽」。
- 与上一轮复审的关系：新问题（上一轮把 row-fingerprint.ts 列入全文精读但未标记此分叉；R5-12 讲的是 rowId 口径，不是指纹公式）。
