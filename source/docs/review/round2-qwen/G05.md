### G05-02 [P2｜已坐实] purge 用 SQL 分词器把反斜杠当字符串转义（与 SQLite 词法分叉），按表删除/重填预清理会漏删触及目标表的 legacy `sql_batch` 语句，残留进回放
- 位置：`source/src/data/repositories/chat-message-data-repo.ts:276-280`（字符串内 `\` + 任意字符按转义消费）、`:354-355`（`!reliable → return []`）、`:455-459`（未判定触及目标的语句被保留）；受影响入口 `purgeSheetKeysFromStorageFrameV2_ACU`（按表删除）与 `purgeManualRefillIncrementalSheetKeysFromStorageFrameV2_ACU`（手动重填预清理）
- 触发：聊天历史里存在 legacy `sql_batch` 操作（无 sheetKey/tableName；今天仍在产生——`buildSqlSheetBatchOperations_ACU` 对无法归属单表的语句走 `appendLegacySqlBatchOperation_ACU`，sql-table-service.ts:1442-1503），其中某条语句含**以反斜杠结尾的字符串字面量**（`'…\'`）或标准 `ESCAPE '\'` 惯用法；用户对这张表执行「按表删除」（数据管理页）或对它做手动重填。
- 现象：SQLite 中反斜杠不是字符串转义符，`'结尾\'` 是合法完整字面量——写入时语句已成功执行过。但 purge 分词器把 `\'` 当转义引号，字符串永不闭合 → `reliable=false` → `extractMutatedSqlTableNamesForPurge_ACU` 返回 `[]` → 语句被判「不触及目标表」保留在 logEntries。此后冷回放会重新执行它：表已从 schema 删除时 `no such table` → 严格回放失败、全表写入门闸 fail-closed（提示「请先执行 V2 恢复诊断」）；若同名表后来被重建（物理表名由显示名拼音确定性派生，sheet-identity.ts:152），残留 INSERT/UPDATE 把已删表的旧数据灌回新表（数据复活）。
- 证据：探针 `probe-G05-purge-residue.ts`（vite-node 调真实 `purgeSheetKeysFromMessageForIsolation_ACU`，已知物理表名 `zhujuexinxibiao`）输出：
  ```
  对照：无反斜杠:   changed=true  残留sql_batch=0 (期望 0)  DELETE FROM zhujuexinxibiao WHERE id = 1
  值以反斜杠结尾:   changed=false 残留sql_batch=1 (期望 0)  DELETE FROM zhujuexinxibiao WHERE note = '结尾\'
  ESCAPE 惯用法:    changed=false 残留sql_batch=1 (期望 0)  UPDATE zhujuexinxibiao SET note = 'x' WHERE note LIKE '%a%' ESCAPE '\'
  ```
- 已排除：`sql_sheet_batch` 不受影响（`purgeSqlSheetBatchOperationV2_ACU:477-483` 先按 sheetKey/tableName 整体删）；写入端分类器用的是**另一份与 SQLite 词法一致**的分词器（`sql-table-service.ts:161-230`：`''` 按双写处理、反斜杠不当转义），能正确分类的语句都带 tableName 不进 tokenizer 防线——所以这是两份重复实现的分叉，purge 侧这份是错的；分叉方向是「保留」不是「多删」，不会直接误删其它表的数据。回放侧症状（no such table → 宽容回放/门闸拒绝；同名重建 → 复活）基于 `applySqlBatchOperationV2_ACU` 入口段与 R3-07/R2B 系列已证实的门闸行为推演，未端到端复现。
- 测试：`chat-message-data-repo.test.ts:1078`（「无法识别的 sql_batch 语句保留原 operation」）用的是 SELECT/CREATE 语句——那是正确的保留；没有「mutation 语句因反斜杠被误判为无法识别」的用例。
- 修法方向：删掉 276-280 的反斜杠转义分支（SQLite 里 `'`、`"`、`` ` ``、`[]` 内都不存在反斜杠转义），或与 `tokenizeSqlMutationIdentifiers_ACU` 统一为一份分词器。
- 与上一轮复审的关系：新问题（block2b 通读过 purge 段未指出；R2B-10 讲的是分句/params 错位，不同点）。

- 触发：宿主文件接口抖动（5xx/超时）时执行向量清理（删聊天 GC、按表删除纪要表、硬清空收尾）：四种 delete 请求体都返回 404（不同宿主 build 接受不同 path 前缀，`:585-587` 注释自证前缀不确定），随后的探测 GET 因网络错误/5xx 返回 false。
- 现象：`deleteVectorIndexFile_ACU` 报 `ok:true` → registry 条目被注销 → 文件实际仍在磁盘上，但后续所有 GC 都从 registry 出发（`:728-746`），永远不再看到它——泄漏不可回收。与同文件 `readVectorIndexJsonFile_ACU:534-556` 明确区分「404=不存在 / 其余=corrupted」的口径自相矛盾。
- 已排除：方向是泄漏不是误删（manifest 引用在严格保存后才摘，聊天数据无影响）；调用方（chat-database-purge.ts:266-296、chat-service.ts:1440-1452）会把 false 记入 cleanupWarnings，但这里返回的是 true，警告通道失效。
