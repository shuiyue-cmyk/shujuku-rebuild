### G07-01 [P1｜已坐实] 固定工作流里「整行契约 → write_sql」混用时，帧重读整份顶掉本地快照：已受理的契约结算数据静默丢弃、其挂账缺口一并消失，完成态误报 no_change，结算水位照推、该段正文永不重结

- 位置：

  最终 settledThroughIndex = 6        ← 水位从 4 推到末楼 6
  最终 pendingFixes = []              ← run1 的挂账缺口一并消失

  对照组（run1、run2 都走整行契约）：`最终 hooks = ["H_RUN1","H_RUN2"]`，数据保留。真实流程中工作流结束时 `agent-main-loop.ts:1792` 把帧基快照落盘，丢失是永久的；水位已越过这段正文，下一轮不再结算。

  ```ts

    const before = snapshot;                    // 本地值：含 run1 契约 delta，hooks rev 已 +1
    snapshot = input.readCommittedSnapshot();   // 帧值：没有 run1 的 delta
    for (const module of writes) {
      if ((snapshot.revisions as any)[module] > (before.revisions as any)[module]) appliedModules.push(module);
  ```

- 已排除：确认 `applyAgentModuleDeltaViaSql_ACU`/`applyAgentWebRefsDeltaViaSql_ACU`/`applyAgentConstraintRegistrationViaSql_ACU` 全链纯函数（agent-transaction.ts 无 saveChat/writeAgentModuleSnapshot）；R4-03 修复（补足通道去掉 write_sql，`agent-main-loop.ts:594-595`）只覆盖编排器补足入口，工作流内部的重派/修复仍持写端口；`:602`（开场检索）发生在任何契约应用之前，无损失；escalate/终审失败等出口都经 `:1792` 落盘本地快照，无损失；run2 若也走契约则本地叠加、无损失（对照组验证）。损失只在「本地契约应用之后又有 field-write 成功提交」的交错点发生，而重派 prompt（`:751`）与运行时 write_sql 提示（`agent-subagent-runtime.ts:636`）恰恰把重试引向这个交错点。

### G07-02 [P2｜已坐实] 工作流把「本地已应用契约 delta」的快照当派工读集传给带 write_sql 的可写子代理：读集修订号超前帧权威，显式 expected_revision 必判 revision_conflict、本地可见而帧不存在的条目 UPDATE 必判 not_found，且重读仍返回本地值，模型无法自愈

- 位置：
  - `source/src/service/continuation/agent/agent-workflow.ts:568-571`（`runSafe_ACU` 把本地 `snapshot` 塞进每次派工）
  - `source/src/service/continuation/agent/agent-main-loop.ts:1727-1728`（`resolveContext: call.snapshot ? { ...context, moduleSnapshot: call.snapshot } : context`）

  - `source/src/service/continuation/agent/agent-module-store.ts:1172-1176`（窗口 head≠帧权威即重置到帧）、`:1244-1255`（自动补号/窗口接管/冲突判定）

- 现象：探针（帧 hooks 修订号 0，窗口/读集为 1）输出：
  ```
  UPDATE 拒绝原因 = [{"path":"hooks#H_RUN1","reason":"revision_conflict: expected=1, actual=0"}]
  INSERT 拒绝原因 = [{"path":"hooks#H_RUN1","reason":"revision_conflict: expected=1, actual=0"}]
  省略修订号 INSERT = committed
  ```
  模型按读取视图写显式 `expected_revision=1` 必被拒；回执告诉它 actual=0，但它重读 `$HOOKS_LEDGER` 仍看到修订号 1（`resolveContext.moduleSnapshot` 要到首次提交成功后才被 `:883` 换成帧）——读集与回执互相矛盾。对「只在本地视图存在」的 run1 契约条目做 UPDATE → `not_found`（`agent-module-store.ts:1257`）。唯一走得通的是省略 expected_revision（帧号自动补，`:1246`），但提示与回执都在教模型「补已有行用回执 revisions 里的模块修订号」。典型后果：白烧 1-2 个写轮后模型改用省略/0 号提交成功——随即落入 G07-01 的替换丢失；或写轮耗尽、修复失败、pendingFixes 留存升级主会话。
- 原因：派工读集/窗口基线来自工作流本地快照，而 `commitAgentModuleFieldWrites_ACU` 的权威比对对象是帧；「本地领先帧」方向上窗口重置（`:1175`）后 `expectedRevision(本地号) > head(帧号)`，接管条件（`:1250-1251`）不满足。
- 已排除：窗口机制在「帧领先本地」方向（上游 5c02f861 的目标场景）行为正确，`agent-dual-mode-s11.test.ts:294-326` 已覆盖自推进接管与外部写入重置；本条只发生在「本地领先帧」方向，而该方向仅由本轮新增的快照传递（`agent-workflow.ts:568-571` + `agent-main-loop.ts:1728`，提交 1b36a19f「维护结算之后…读到的是刚结算好的资料」）构造——对纯 write_sql 链路（重读即帧）该改动是正确修复，混用链路未顾及。契约 SQL 的 `expectedRevisions` 校验（`agent-subagent-runtime.ts:991-997`）与本地快照同源自洽，且提交成功后契约必须为空（弹回门），不构成额外冲突面。
- 测试：无「窗口/读集基线超前帧」方向的测试（现有窗口测试只测落后与持平）。
- 修法方向：与 G07-01 同源——契约 delta 即时落帧则读集与帧天然一致；或只对**可写**角色派工时用帧权威快照做 `resolveContext.moduleSnapshot`（策划/编排/终审等只读角色继续用本地最新值，保住 1b36a19f 的修复收益）。
- 与上一轮复审的关系：新问题（本轮改动引入的混用路径副作用；改动本身对 write_sql 主路径是修复）。

### G07-03 [P2｜已坐实] 手动并行派工批的结算同构互踩：先结算的整行契约派工数据被后结算的 field-write 派工帧重读静默顶掉（该派工已向主会话报「已结算 N 条」）；反序时契约 delta 撞上被帧推进的修订号整单被拒
