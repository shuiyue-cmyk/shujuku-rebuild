## 发现

### G08-01 [P1｜已坐实] 「常用世界书」复制正在被 Agent 接管的源书时，副本原样带上「已禁用 + 他人接管账本」，挂上新卡即整本死书

- 位置：
  - `source/src/service/agent/agent-favorite-worldbooks.ts:80-84`（`isAgentRuntimeEntry_ACU` 只按 comment 前缀过滤整条目）、`:87-93`（`buildFavoriteWorldbookCopyData_ACU`）、`:143`（`saveWorldbookFile_ACU(targetName, buildFavoriteWorldbookCopyData_ACU(source))`）
  - 判定依据：`source/src/service/agent/agent-skillify-service.ts:150-155`（`isWorldbookEntrySkillifyCandidate_ACU` 排除 `enabled === false`）、`source/src/service/agent/agent-worldbook-takeover.ts:885-944`（接管禁用会把条目写成 `enabled:false` 并在 comment 追加接管 meta 块）
  - 误导显示：`source/src/presentation-v3/pages/AgentPage.vue:358-365`（`favoriteBadge`，candidateCount=0 → 「无可 Skill 化条目」）
- 触发：常用世界书的功能主路径。卡 A 处于 Agent 模式、技能书 S 在 A 的作用域内——**此时 S 的全部 skill 条目被接管禁用（enabled=false + comment 内嵌接管 meta），这是 Agent 模式的常态，且切聊天/切卡都不会恢复（a8995d17 明确「不动接管账本」）**。用户打开卡 B → Agent 页「常用世界书」勾选 S → 点「挂载所选到当前角色卡」。
- 现象：副本「B-S」里每个 skill 条目都是 `enabled:false` 且 comment 带着卡 A 作用域签名的接管 meta 块：
  1. 条目禁用 → 原生生成不注入，副本对卡 B 的普通聊天完全无效；
  2. 卡 B 的接管/Skill 化都救不回来：`collectTakeoverCandidates_ACU`（takeover:763-785）和 skillify 候选（agent-skillify-service.ts:435-443）都走 `isWorldbookEntrySkillifyCandidate_ACU`，禁用条目被排除；
  3. 副本里的接管 meta 签名与卡 B 作用域签名不匹配，任何账本读取（takeover:632-634、656-657）都忽略它 → 没有恢复路径；「退出接管」也只按账本恢复，够不到这些条目；
  4. 常用面板对源书 S 的徽标同时显示「无可 Skill 化条目」（候选统计同样排除禁用条目），用户无从察觉副本已死。
  与提交 60e43673 宣称的「复制时不带数据库生成条目和**别的卡的 Agent 状态**」直接矛盾：实现只过滤了独立的内部条目（comment 以 `TavernDB-ACU-` 开头的配置/快照/绿灯条目）和数据库生成条目，**条目级的接管状态（禁用开关 + 内嵌 meta）原样复制**。
- 原因（关键代码，agent-favorite-worldbooks.ts:80-84）：
  ```ts
  function isAgentRuntimeEntry_ACU(entry: Record<string, any>): boolean {
    const comment = String(entry?.comment ?? '').trim();
    // 数据库生成条目与 Agent 每卡状态（配置、快照、绿灯）都不属于常用书内容，复制会把别的卡的状态带过来。
    return comment.startsWith('TavernDB-ACU-') || isDatabaseGeneratedLorebookEntry_ACU(entry);
  }
  ```
  接管 meta 是**追加在普通用户条目 comment 尾部**的 HTML 注释块（takeover:443-457 `buildTakeoverMetaComment_ACU`），comment 开头是用户原文，前缀过滤命不中；`enabled:false` 更是完全没被处理。
- 证据：探针 `probe-G08-favorite-copy.test.ts`（已删）。构造源书条目 `enabled:false` + comment 含 skill 块和接管块，走 `mountFavoriteWorldbooksToCurrentCharacter_ACU` 全流程：副本条目 `enabled=false`、comment 含 `ACU_AGENT_WORLDBOOK_TAKEOVER_META_START`（探针输出 `copied entry enabled = false`、`copied comment has takeover meta = true`）；Agent 状态条目（uid 2）确被过滤，证明只挡了独立条目。
- 已排除：查了 `mountFavoriteWorldbooksToCurrentCharacter_ACU` 全流程（agent-favorite-worldbooks.ts:115-162），复制前后没有任何剥离/还原步骤；`isDatabaseGeneratedLorebookEntry_ACU`（worldbook-placeholder-classification.ts:61-67）只看归一化 comment 前缀，接管块在尾部命不中；`saveWorldbookFile_ACU`/`loadWorldbookFile_ACU`（worldbook-file-gateway.ts:44-57）是整本原样读写，不改条目字段。副本条目保留 skill meta，用户手动启用后可被卡 B 重新接管（`buildTakeoverMetaComment_ACU` 会先 strict 剥掉旧块），但这是两步手动补救，不是产品承诺的行为。
- 测试：`source/tests/service/agent/agent-favorite-worldbooks.test.ts:99-115` 只覆盖「数据库生成与 Agent 状态条目（独立条目）不复制」，构造的源书条目全是启用态、无接管 meta；没有任何用例构造「源书正在被接管」。
- 修法方向：`buildFavoriteWorldbookCopyData_ACU` 对每个保留条目做接管态物化还原——有接管 meta 的：按 meta 里的 `previousEnabled/previousKeys/previousType` 还原字段并 strict/loose 剥掉 meta 块；或至少在挂载前检测源书处于接管中并提示先「退出接管」。
- 与上一轮复审的关系：新问题（60e43673 新功能）。

### G08-02 [P1｜已坐实] 挂载常用书（或宿主任意增删绑定书）改变作用域签名后，旧签名下被接管禁用的条目永久孤儿化：新账本不含、退出接管不恢复，一旦有新候选触发账本改写即不可逆

- 位置：
  - `source/src/service/agent/agent-worldbook-takeover.ts:1313`（`shouldReconcileExistingActiveSnapshot` 要求签名一致才 reconcile）、`:632-634`（持久账本按新签名判定，旧签名一律视为 null）、`:656-657`（条目内嵌 meta 同样按新签名过滤）
  - `source/src/service/agent/agent-worldbook-config-meta.ts:692-724`（「先恢复再换范围」只存在于 **control patch 显式携带 worldbookScope 变更** 的路径：`:666-668` `changesScope` 的判定要求 `hasExplicitWorldbookScope_ACU(patch.control)`）
  - 新增触发面：`source/src/service/agent/agent-favorite-worldbooks.ts:155`（`addAuxWorldbookToCurrentCharacter_ACU` 直接改宿主角色卡绑定，不经过任何接管协调）
- 触发：当前角色卡 Agent 模式接管活跃（scope=跟随角色卡，条目已禁用、账本 active、签名 = 旧书单哈希）。用户在 Agent 页点「挂载所选到当前角色卡」（副本被追加为附加世界书 → 角色绑定书单变化），**或者**用户直接在宿主 UI 里给这张卡加/删一本附加世界书。随后任何一次接管运行（下一轮剧情推进、或挂载后 `refreshAll` 触发的快照刷新）按新书单算出新签名。
- 现象：
  1. 旧签名账本立即失配：内存快照被刷成 inactive，`isWorldbookTakeoverActive_ACU()` 变 false；
  2. 原书里被禁用的条目**不在任何账本里**（新账本按新签名重建，旧 meta 全部被 `:657` 跳过），也不会被 reconcile 恢复（`:1313` 签名不一致直接跳过）；
  3. 「退出接管」`restoreWorldbookGreenlights_ACU` 按当前签名读账本 → `shouldRestoreSnapshot=false` → 什么都不恢复（reason='no_active_snapshot'），条目保持 `enabled:false` + 残留接管块；
  4. 若失配期间任何一次接管运行找到了新候选（新书里/主书里还有启用的 skill 条目），`workingSnapshot` 会**改写持久账本为新签名**（takeover:1325-1335、1388-1399），旧账本被覆盖，孤儿化不可逆；若没有新候选，账本暂存旧签名，撤掉绑定变化还能自愈——用户对此毫无感知，也无从分辨。
  5. 用户视角：挂载常用书（或整理绑定书）之后，原技能书在生成里静默消失，Agent 决策也永远看不到它们（禁用条目不进候选，见 G08-01 第 2 点），没有任何报错。
- 原因（关键代码，takeover:1313）：
  ```ts
  const shouldReconcileExistingActiveSnapshot =
    existingSnapshot.active === true && existingSnapshot.selectionSignature === selectionSignature;
  ```
  签名是作用域书单的哈希（shared/agent-worldbook-snapshot），**书单被宿主侧改变时没有任何「按旧账本先恢复」的入口**——config-meta 的恢复协调只挂在 UI 显式改 scope 的写路径上，绑定变化绕过了它。
- 证据：探针 `probe-G08-scope-orphan.test.ts`（已删，mock 口径与仓库 `agent-worldbook-takeover.test.ts` 同构）。接管生效（uid1 disabled）→ 作用域书单从 `['原书S']` 变 `['原书S','副本S']`（副本S 带启用 skill 条目，模拟挂载）→ 再接管：原书 uid1 仍 `enabled:false`，新账本只含 `副本S`；→ 退出接管：原书 uid1 仍 `enabled:false` 且 comment 仍含接管块（探针输出逐段确认）。
- 已排除：确认 `restoreAgentWorldbookSnapshotEntries_ACU` 的唯一调用方是 config-meta 的显式 scope 变更路径（grep 全库）；`reconcileExistingTakeoverSnapshotWithSkillMeta_ACU` 只在签名一致时执行；`readPlotAgentWorldbookSnapshotFromStateOrLegacy_ACU` 的 stale-book 剪枝（takeover:670-688）只处理「书不存在」，不处理「书单多了/少了」；R4-04 修复的 missing 收敛（takeover:975-977）针对条目被删，与本条的签名失配是两条路。挂载流程（useFavoriteWorldbooks.mountSelected → mountFavoriteWorldbooksToCurrentCharacter_ACU）全程没有检查当前卡是否处于接管中。
- 测试：`agent-worldbook-takeover.test.ts` 覆盖了换角色卡收回绿灯、删条目收敛、comment 改动跳过等，但没有「作用域书单被外部改变（绑定变化）」的用例；`agent-worldbook-config-meta.test.ts` 只测显式 scope 写路径的恢复。
- 修法方向：接管/刷新入口发现 `state.snapshot.active === true && state.snapshot.selectionSignature !== 新签名` 时，先按旧账本对旧书单执行恢复（复用 restore-core），再重建新签名账本；退一步至少：常用世界书挂载前检测当前卡接管活跃，先 `restoreWorldbookGreenlights_ACU` 或阻断并提示。
- 与上一轮复审的关系：新问题。机制本身在基线前就存在（宿主 UI 手动改绑定同样触发），block4 未记录；本次新功能第一次把「改绑定」做进了插件内部，触发概率大增，且两个 P1 同属「常用世界书 × 接管状态机」的协调缺失。

## 设计层面的疑虑（不计入缺陷）

1. **冷启动重新生成的「放行保留」只保物理灯，不保名单**：页面刷新后 `pendingFinalGenerationGreenlights_ACU` 恒为空，靠「过滤目录排除 constant」让物理绿灯存活（见跨组线索 3）。这套双轨（物理灯给宿主注入用、内存名单给过滤器用）没有单一真源，G08-06 的时序疑点和跨组线索 3 都是它的副产物。把 `readFinalGenerationGreenlights_ACU` 接到冷启动水合上（回填内存名单）可以消掉整类问题。
2. **接管期间用户手改条目 type/keys 会被静默回退**：`buildGreenlightReleasePatch_ACU`（takeover:231-245）与 `decideAgentWorldbookEntryRestore_ACU`（restore-core:106-115）都按账本 `previousType/previousKeys` 回写；commentHash 只保护 comment，不保护 type/keys。用户在接管期间于原生编辑器把条目改成常驻，下一轮清绿灯/退出接管时会被改回。与既有恢复语义一致（08b7300e 有意为之），但对用户是无提示的。
3. **切聊天物理收回是 fire-and-forget**：`releaseAgentGreenlightsOfPreviousChat_ACU`（injection-engine-state.ts:75-80）失败只 warn，靠「下一轮剧情推进开头再清」兜底。窗口期内若相关书被全局激活（`selected_world_info`），亮着的 constant 条目会注入到无关聊天。窗口短、方向保守，接受但记录。

## 复核过但判定没问题的可疑点

1. **「冷启动重新生成会丢绿灯」的怀疑（曾接近立案）**：`handleChatCompletionReady_ACU`（helpers-remaining.ts:218-236）冷启动水合后以空放行名单跑过滤，一度怀疑会把物理亮着的绿灯条目从提示词里剥掉。查证 `isAgentControlledFinalPromptWorldbookEntry_ACU`（plot-task-engine.ts:172-177）**排除 constant 条目**，而物理绿灯恰为 enabled+constant → 不进过滤目录 → 重新生成保留放行内容。排除。
2. **切聊天收回与在途绿灯写入的竞态**：`runExclusiveAgentWorldbookOperation_ACU`（operation-lock.ts:18-23）FIFO 串行；`applyAgentFinalGreenlights_ACU`（plot-task-engine.ts:1018-1035）写前写后双查 `isRuntimeScopeCurrent_ACU` 并在失配时清名单。旧聊天写入要么排在 release 之前（随后被 release 关掉），要么被作用域检查拦下。没找到「release 之后旧聊天把灯重新点亮」的序列。
