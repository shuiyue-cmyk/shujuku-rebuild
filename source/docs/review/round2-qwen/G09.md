### G09-01 [P1｜已坐实] 可视化编辑器「新增列」从不同步 DDL，之后模板保存在任何模式下都必然被拒，新增列功能整体不可用

- 位置：
  - `source/src/presentation-v2/composables/visualizer/useVisualizerConfigEditing.ts:276-286`（`addColumn` 只 push 表头与行单元格，不碰 `sourceData.ddl`）
  - 对照同文件：`updateHeader` 同步 DDL 注释 `:266-272`；`deleteColumn` 原子同步 DDL `:296-309`
  - 拒绝点：`source/src/presentation-v2/composables/visualizer/useVisualizerSave.ts:697-701`（preflight 调用）→ `:746-753`（blockers toast「模板结构未通过 schema migration preflight：…」）；新增表走 `:848`→`prepareTemplateSheetsForCommit_ACU:259-280`（`:275` 只在 DDL 为**空**时补生成，`:276-277` 陈旧 DDL 校验失败即 throw）
  - 判定链（跨组，只读确认）：`source/src/service/table/table-schema-migration.ts:32-45`（`requireSheetShape_ACU` DDL/表头强校验）→ `source/src/service/table/schema-migration-planner.ts:55-62`（descriptor 抛错 → `invalid`，不可 rebase）→ `source/src/service/table/schema-migration-preflight.ts:158-169`（invalid → 最终 blocker）
  - UI：`source/src/presentation-v3/surfaces/visualizer/VizConfigView.vue:21-23`（「新增列」按钮无模式门禁、文案承诺「已有数据行会自动补一个空值」）；`:82`（DDL 编辑区 `v-if="config.isSQLite.value"`，native 模式不可见）；`source/src/presentation-v3/surfaces/VisualizerSurface.vue:282-292`（弹窗文案「新列加在表头末尾…保存前只改动草稿」）
- 触发：数据库编辑器 → 任一表 →「结构」页 →「新增列」→ 输入列名确认 →（底部）「保存模板到当前聊天」或「保存模板到全局」。
- 现象：保存必然失败。已有表（含新建表）报「模板结构未通过 schema migration preflight：sheet_x: schema descriptor V2 DDL/表头不一致：⚠ DDL 列名与表头不完全匹配：列数不匹配：DDL 有 N 列，表头有 N+1 列」（探针 3 原文）；本次会话新建的表（added sheet 被 preflight 排除，因 baseline 无此 key）则报「模板保存被拒绝：sheet_x 的 DDL 无法 strict hydrate：列数不匹配…」。若表本来就没有 DDL（native 模式部分导入模板），报「…DDL/表头不一致：⚠ DDL 为空」（探针 1 用例 4）。用户唯一出路是丢弃草稿；SQLite 模式下理论上可在 DDL 编辑区手写补列自救，但错误文案不指向它，且与「新增列」按钮的存在意义相悖；**native 模式下 DDL 编辑区被隐藏（VizConfigView.vue:82），完全无法自救**。
- 原因：`addColumn` 与 `updateHeader`/`deleteColumn` 的 DDL 同步义务分叉。全库不变式是「DDL 与表头逐列一致」——改表助手 v3 协议对 AI 也是这么要求的（`source/src/service/template-assistant/service.ts:649`「sourceData.ddl 必须非空且完整，与 content 表头逐列匹配」），v2 编译甚至硬性规定「DDL 表执行增删列时必须同时提供 patch.ddl」（`source/src/service/template-assistant/compiler.ts:521-523`）。唯独手动 `addColumn` 漏掉：

  ```ts
  function addColumn(name: string): void {
    const normalizedName = name.trim();
    if (!normalizedName) return;
    withSheet(sheet => {
      const content = ensureSheetContent(sheet);
      content[0].push(normalizedName);
      content.slice(1).forEach((row: any) => {
        if (Array.isArray(row)) row.push(null);
      });
    });   // ← 没有任何 sourceData.ddl 处理
  }
  ```
- 覆盖面：默认模板所有表两种模式下都自带 DDL（`source/src/shared/table-defaults/*.js:13`）；编辑器新建表也生成 DDL（`useVisualizerData.ts:73`）；模板保存过的表由 `prepareTemplateSheetsForCommit_ACU:275` 补上 DDL 并随 `targetSheetData` 持久化。因此「有 DDL 的表」是绝对主流，本缺陷几乎必现。
- 已排除：查过 `addColumn` 全部调用点（仅 `VisualizerSurface.vue:291`）与 `withSheet`/store 链路，无任何后置 DDL 再生成；`saveTemplateToCurrentChat` 中 preflight（`:697`）先于唯一会补 DDL 的 `prepareTemplateSheetsForCommit_ACU`（`:848`），且后者只补**空** DDL、不修陈旧 DDL；`preflightSchemaMigrations_ACU` 对 planner `invalid` 不给 rebase/needs_choice 出口（fail-closed 语义本身正确）。
- 测试：`source/tests/presentation-v2/visualizer/use-visualizer-config-editing.test.ts:112-120`「新增列会同步所有数据行」只断言 content，不断言 DDL（同文件 `:84-94`、`:122-132` 对 updateHeader/deleteColumn 都断言了 DDL 同步——唯独 addColumn 没有）；`source/tests/presentation-v2/visualizer/use-visualizer-save.test.ts:126、232-233` 把 `preflightSchemaMigrations_ACU` 整体 mock 掉，schema 用例（`:840-847` 等）全部手写同步好的新 DDL，「addColumn → 真实保存」链路零覆盖。
- 修法方向：`addColumn` 内与 deleteColumn 同规格处理 DDL——已有 DDL 时按现有列样式追加列定义（或整表 `generateDDL` 重建，需保留既有约束/注释），无 DDL 时先生成；顺带把「结构操作后 DDL 必须与表头一致」做成三个操作共用的收尾函数，并对「改成重复列名」在编辑器内即时校验（现在也是拖到保存才报 DDL 表头重复）。
- 与上一轮复审的关系：**新问题**（block10A 审过本文件的 renameSheet/updateHeader，未涉及 addColumn 的 DDL 义务）。

### G09-02 [P1｜已坐实] 手动混合编辑（数据增量＋模板变化）后三条保存路径循环互拒，整份草稿无路可存、只能全部丢弃；两条错误文案互相指引对方被拒的动作

- 位置：
  - 数据保存守卫：`source/src/presentation-v2/composables/visualizer/useVisualizerSave.ts:417-428`（`(hasDataChanges || hasLockChanges) && hasPendingTemplateChanges` → 「数据保存不能混入未提交的模板变化；**请先保存模板，再保存数据**。」，R10A-02 修复引入）

- 触发：打开数据库编辑器，在**同一次会话**里既改数据又改结构——例如改掉某行一个单元格（产生 pendingDataOps），再把表改个名（产生模板 metadata 变化）；然后点任意保存。
- 现象（探针 2 实测）：「保存数据到当前消息」→ false，提示「…请先保存模板，再保存数据」；照做点「保存模板到当前聊天」→ false，提示「存在未保存的数据增量；…已阻止混合提交」；「保存模板到全局」→ 同样拒绝；关闭编辑器选「保存」→ 还是数据路径 → 同样拒绝。三条路的提示互相矛盾成环，零提交发生，`store.dirty` 保持 true。用户唯一出路是「丢弃草稿」，本次全部编辑（含与冲突无关的改动）一起丢失。删过行的场景连手工逆转都不可能（行已从草稿消失、删除 op 已入队）。
- 原因：R10A-02 的修复方向（block10A 原文建议「数据路径只要检测到 hasPendingTemplateChanges 就拒绝，并提示先保存模板」）与模板路径既有的「拒绝数据增量」守卫（`:638`）组合成循环：数据路径要求先存模板，模板路径要求先清数据增量，而两者都无「分步保存」出口。R10A-05 对 AI 助手草稿的同构死锁做了处理（应用前拦截并提示分两步，`useVisualizerAssistant.ts:363-379、858-861`），手动编辑路径漏掉了。
- 已排除：确认页脚/关闭守卫没有其他保存入口；确认 pendingDataOps 无「净零自动清除」（把值改回原文，op 仍在队列，`visualizer-data-ops.ts:133-146`）；确认模板变化分类不忽略任何一类（改名、列、顺序、mate 全覆盖）；锁改动＋模板变化可经模板路径一起保存（`:662-674`），死锁只由行级数据增量触发。
- 测试：`source/tests/presentation-v2/visualizer/use-visualizer-save.test.ts:305-325`「数据保存不会把同时存在的模板变化标成已保存」恰好构造了同一混合态，但只断言数据侧拒绝，从未再调模板保存验证可走通；全库无任何测试断言「存在未保存的数据增量；…已阻止混合提交」这条文案（grep 0 命中）。
- 修法方向：给出真正的分步出口——例如模板保存时若数据增量只落在**本次未变更结构**的表上则允许一并原子提交或先行提交数据；确实无法原子化时，把两条文案改成一致的、可执行的指引（如「表 X 同时有结构改动和行改动，请先撤销其中一类」并列出冲突表），而不是互相指向对方被拒的动作。
- 与上一轮复审的关系：**R10A-02 修复不完整**（修复本身正确堵住了「吞模板改动」，但按 block10A 给出的修法落地后与既有模板守卫构成死锁环，未提供出路）。
