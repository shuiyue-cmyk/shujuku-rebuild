### G13-01 [P2｜已坐实] 外观抽屉的「界面模式」切换绕过未保存关闭守卫，页内草稿静默丢失（R10B-06 修复不完整）

- **位置**：
  - `source/src/presentation-v3/shell/AppearanceSheet.vue:138-141`（`setMode` 无守卫直接切）、`:72-80`（「界面模式」UbSegmented 绑定 `setMode`）
  - 对照（同类入口都过了守卫）：`source/src/presentation-v3/App.vue:181-187`（`toggleMode` 先 `await canLeaveCurrentPage()`）、`source/src/presentation-v3/shell/NavList.vue:65-69`（`go`）、`source/src/presentation-v2/surfaces/visualizer/open-visualizer-surface.ts:53-60`、`source/src/presentation-v2/composables/useTablePresetManagement.ts:168,188`
  - 会被静默丢掉的守卫方：`source/src/presentation-v3/parts/ApiPresetEditor.vue:475-483`、`pages/VectorIndexPage.vue:304`、`pages/TablePage.vue:260`、`pages/ContentReplacePage.vue:486`、`parts/PlotPresetSection.vue:178`；基础模式同样受害：`pages/BasicConfigPage.vue:3` 内嵌 `ApiPresetEditor`（id-prefix basic-api）、`:6` 内嵌 `PlotPresetSection`
- **触发**：高手模式下在「API」页改了预设的 URL / Key / 模型（底栏出现「有未保存的修改」），不点保存 → 点侧栏底部「外观与界面」→ 在抽屉里把「界面模式」切成「基础」。反方向同样成立：基础模式下在基础配置页改 API 草稿（或打开剧情预设抽屉改了内容）→ 外观抽屉切「高手」。
- **现象**：模式立即切换、`ensureActiveVisible` 把 `activePageId` 换成 basic-config / dashboard，App.vue 的 `<component :key>` 变化导致旧页**当场卸载**，草稿丢失，全程没有任何确认弹窗。而同一个切换走侧栏「返回基础模式」按钮时会弹「你有未保存的 API 修改，确定要关闭吗？」。
- **原因**：`setMode` 是 R10B-06 修复时漏掉的第四个换页入口：

  ```ts
  // AppearanceSheet.vue:138-141
  function setMode(value: string): void {
    uiMode.setMode(value as AcuV2UiMode);
    router.ensureActiveVisible();
  }
  ```

  守卫集合只在 `canCloseUi()/canLeaveCurrentPage()` 被消费；`uiMode.setMode` + `ensureActiveVisible` 都不经过它们，页面卸载时守卫随 `onBeforeUnmount` 注销，从未被询问。
- **已排除**：grep 全库 `canLeaveCurrentPage` 全部 5 个调用点（NavList.go、App.toggleMode、open-visualizer-surface、useTablePresetManagement×2），确认外观抽屉不在其中；grep `uiMode.setMode|toggleMode` 确认模式切换只有 App.vue 与 AppearanceSheet 两个入口，前者有守卫后者没有；确认基础↔高手两个方向都必然换页（`router-store.isPageVisible` 在基础模式只放行 basic-config，高手模式隐藏 basic-config），不存在「切了但页面没卸载」的豁免路径；App.vue:233 的 `watch(uiMode.mode)` 只补 `ensureActiveVisible`，同样不过守卫。
- **探针**：`zz-probe-G13-appearance-mode.test.ts`（基于 `tests/presentation-v3/v3-harness.ts`）。挂载 v3 → 切到 api 页 → `registerUiCloseGuard(() => false)` 模拟脏草稿：①点侧栏「返回基础模式」→ guard 被调 1 次、仍停在 api 页、仍显示「高手模式」（守卫生效）；②打开外观抽屉点「界面模式 → 基础」→ guard 调用次数**仍为 1**、`uiMode.mode === 'basic'`、`router.activePageId === 'basic-config'`（守卫被绕过）。1/1 通过，复现成立。探针正本与全文见「探针」一节；仓库内副本跑完即删，`git status` 已确认干净。
- **测试**：`source/tests/presentation-v3/shell.test.ts:70-98`「R10B-06：页内有未保存修改时，切页与切模式先过关闭守卫」只覆盖侧栏切页与侧栏模式按钮两个入口，外观抽屉入口无用例，因此没拦住。
- **修法方向**：`setMode` 改成 async，先 `if (!(await canLeaveCurrentPage())) return;` 再切（与 `App.toggleMode` 同构）；更彻底的做法是把「切模式」收敛为 ui-mode-store / router-store 的一个带守卫动作，两个入口共用。
- **与上一轮复审的关系**：**R10B-06 修复不完整**（当时列出的三处入口 + 外部 API 开编辑器都接了守卫，外观抽屉这处模式切换被遗漏）。

### G13-02 [P3｜已坐实] 日志处理建议指向从未存在过的「固化兼容回放为过渡根」按钮，兼容只读场景用户照做走进死胡同

- **位置**：`source/src/presentation-v2/composables/log-error-hints.ts:249-258`（`v2-compat-readonly` 规则），问题步骤在 `:255`：

  ```ts
  '到「数据管理」→「诊断 V2 数据恢复」，点「固化兼容回放为过渡根」：把当前兼容读取结果写成严格可回放的根，之后写入与追平恢复正常（含 sheetKey 身份归并时需要额外确认）。',
  ```
- **触发**：聊天表格历史进入 Tier-1 兼容宽容回放（典型：历史里重复插入同一 row_id 导致严格回放失败），填表 / 追平 / 模板提交被拒绝并记 error 日志；用户在「高级工具 → 运行日志」里对这条报错展开「怎么处理」。
- **现象**：按建议操作会失败——
  1. 全库不存在名为「固化兼容回放为过渡根」的按钮。`git log -S` 证实该字符串自 e8e80511（2026-09-08）引入以来只出现在 log-error-hints.ts 一个文件里，任何版本的 DataMgmtPage 都没有过它。
  2. 实际 UI：入口行叫「历史恢复诊断」、按钮叫「诊断」（DataMgmtPage.vue:15-23）；诊断后出现「V2 数据恢复诊断」分节（:58-81），按钮全集是「导出已保存的原始 frame 备份」＋按状态显示的「应用 Checkpoint 修复/收敛」「确认无锚点 data_replace 恢复」。

- **原因**：文案写的是设想中的交互，从未与真实 UI 对齐；规则匹配测试只验证「这类报错命中这条规则」，不验证步骤里的界面元素是否存在。
- **已排除**：grep 全库 `固化兼容回放|过渡根`——UI 层（presentation / presentation-v3）无该文案按钮；读 DataMgmtPage.vue:58-95、:183-230 确认恢复分节按钮全集与状态白名单；读 table-v2-recovery-service.ts:495-640 确认 compat 分支不产出 plan；grep `身份归一化` 确认相关指引只存在于 service 报错文案（同样指向不存在的 UI，见跨组线索）。建议第 3 步提到的「导出已保存的原始 frame 备份」按钮真实存在（DataMgmtPage.vue:61），不受影响。
- **测试**：`source/tests/presentation-v2/log-viewer/log-error-hints.test.ts:52-53` 用真实报错文本断言命中 `v2-compat-readonly`——它锁定了规则匹配，无法也不曾校验 steps 文案与 UI 的一致性，所以没拦住。
- **修法方向**：第 2 步改为真实路径与真实行为：「到『数据管理 → 备份与恢复』点『历史恢复诊断』下的『诊断』查看收敛状态；不含 sheetKey 身份归并的历史会在重新加载聊天后自动固化，稍后重试写入即可；诊断显示含身份归并时当前版本无法自助修复，请导出日志与原始 frame 备份反馈作者」。service 层同款过时文案一并修（跨组）。

## 设计层面的疑虑（不计入缺陷）

1. **`stores/persistence.ts:31-58` 的内存回退是「只写不读」的半截兜底**：`writeAll` 在 `setItem` 抛错（如配额满）时把状态存进 `memoryFallback`，但 `readAll` 只要 storage 可读就永远不查 `memoryFallback`（且 `!raw` 时直接返回 `{}`）。后果：写失败后，`readPersistedEffectiveTheme_ACU`（bootstrap/index.ts:85-89 的系统明暗监听、启动上色）会继续按旧值给面板外浮层上色，与面板内 store 状态短暂分叉。触发前提（localStorage 可读但写入失败）罕见、影响仅外观，故不计缺陷；建议 readAll 在 storage 值缺失/陈旧时合并 memoryFallback，或删掉这个误导性回退。
2. **`useDashboardPage.setToggle` 的 5 处 fire-and-forget `saveSettings_ACU()`（:1091-1107）**：`storage_error` 时开关的内存值已改、UI 显示新状态，但重启后回落，用户无提示（错误只进运行日志）。`settings_loading` 情形 service 已有「就绪后自动补存」兜底。同款写法在 G03/G05 等组的 composables 里普遍存在，上一轮只对「失败仍弹已保存」的 store 修了（R10B-12），此处不弹成功、只静默，量级更轻——留给协调者决定是否全库统一。
3. **gate 同步的强制收页不过守卫**：`router-store.syncFeatureGate* → ensureActiveVisible`（:140-165）在「当前页入口被隐藏」时直接切回默认页，不询问关闭守卫。这是 R10B-20 修复明确选择的行为（「入口被隐藏时收回当前页」），且需要「别处改了设置 + 恰逢切聊天/重开面板 + 当前页恰好脏」的并发窗口才可能丢草稿，维持原设计不报。

 * zz-probe-G13-appearance-mode — 验证 AppearanceSheet「界面模式」切换绕过 useUiCloseGuard。

import { afterEach, describe, expect, it, vi } from 'vitest';
import { byText, flush, mountV3 } from './v3-harness';

let cleanup: (() => void) | null = null;
afterEach(() => { cleanup?.(); cleanup = null; });

describe('probe-G13：外观抽屉切界面模式绕过关闭守卫', () => {
