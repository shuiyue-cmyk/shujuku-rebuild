## 设计层面的疑虑（不计入缺陷）

1. **重新生成前的立即刷新会阻塞宿主正文请求，时长随聊天规模增长**：`init.ts:1290-1295` 在 regenerate 的首次 MESSAGE_DELETED 上当场 `await flushChatMutationRefreshNow_ACU()`，一轮包含删楼 checkpoint 前移恢复 + SQLite 冷重建 + 合并刷新（含世界书），即两次全量回放；大聊天（数百楼、多表）时用户点「重新生成」到正文开流之间可能停顿数秒且无任何进度提示。这是 UPSTREAM-DRIFT #56 记录的刻意取舍（正确性优先），只提示：若日后收到「重新生成变卡」反馈，这里是量级来源。
2. **交火索引重建确认框会把宿主 Generate 挂起直到用户点击**（`summary-vector-index-ui.ts:168`，在 GENERATION_AFTER_COMMANDS 监听内 await）：无超时、无取消联动。属「必须取得用户同意才重建（embedding 费用）」的预期行为，但与疑虑 1 叠加时（先重建确认、再生成）用户体感停顿更长。
3. **`foregroundTurnStopped_ACU`（init.ts:629）切聊天时不复位**：停止后切聊，标志残留到下一次前台 STARTED 才清。残留期间只会**多跳过**无配对的伪 ENDED（fail-safe 方向，且这类事件本来就被 `markChatChangedForEndedGate_ACU` 基线窗口挡掉），未发现可达的漏填表路径，故不计缺陷；若追求整洁可在 CHAT_CHANGED 同步段复位。
