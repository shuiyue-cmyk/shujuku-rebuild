你是这次复审的**协调者**。

- **范围**：这次不是全库复审，审的是**填表的全流程**：触发与调度、AI 请求与回复解析、写入与提交、存盘与回放、收尾副作用，以及相关界面。
- **重点**：用户在填表进行到一半时做出的「奇怪操作」，见 2.4 的三个重点。
- 其他填表相关的问题同样要报。

整个流程分三个阶段，**顺序不能乱**：

1. **发现**（第三节）：按分组派子代理找问题，各写一份分组报告。
2. **复核**（第五节）：每份分组报告交给**另一个**冷启动的子代理逐条复核，判定成立 / 不成立。**没有经过复核的条目不能进最终报告。**
3. **出报告**（第六节）：你只根据复核结论写总报告。

几点要求：

- **你自己不逐行审代码**，只派活、合并、抽查。
- 子代理是冷启动的，看不到这份文档。所以派活时，提示里都要原样转发**第二节「共同规则」全文**（不要删减），再加上该子代理的专属内容：
  - 发现阶段：加上该组在第三节的那一行。
  - 复核阶段：加上第五节全文，以及要复核的分组报告文件名。
- 并发上限不够时，派不下的排队，前面的做完再接着派。

这份报告最后会由另一位工程师逐条核查。没有证据的条目、编造的行号、把设计取舍当缺陷的条目，都会被直接判为误报。**宁可少报，不要凑数。**

### 2.2 项目背景

- **是什么**：UnbirthDB，一个 TauriTavern（SillyTavern 的 Tauri 移植版，以下简称 TT / ST）前端扩展。
  - 它在聊天消息里保存 SQL 表格数据（sql.js / SQLite）。
  - 每轮 AI 回复后自动「填表」：把新楼层交给另一个 AI，按回复修改表格，再把结果写进楼层并存盘。
  - 用户也可以手动填表、重填（先清掉再填）、一键追平（把没填过的楼层批量补上）。
  - 用户基本都是无技术背景的角色扮演玩家，会做出各种「不按套路」的操作。
- **目录**（仓库根目录就是含 `manifest.json` 的那一层）：
  - `source/src/`：全部源码，约 19.3 万行 ts / vue / js。入口是 `entry-extension.ts`。
  - `source/tests/`：vitest + jsdom，约 490 个测试文件。读测试是弄清「预期行为」最快的办法。
  - 根目录的 `index.js` 是打包产物，**不要审**。
- **命名约定**：大量函数和常量带 `_ACU` 后缀，这是历史前缀，不算问题。
- **可用命令**（在 `source/` 目录下执行）：
  - 类型检查：`npm run typecheck`
  - 单个测试：`npx vitest run tests/路径/xxx.test.ts`
  - 不要跑全量测试：耗时长，而且多个子代理同时跑会互相拖慢。

### 2.3 宿主事实（判断时以此为准）

1. **ST / TT 切聊天时复用同一个 `chat` 数组对象**：先清空，再把新聊天的楼层放进去。所以：
   - 代码里早先拿到的数组引用，切聊天后会指向新聊天的楼层；
   - 只比较数组引用识别不出切换。代码里用「聊天身份 + 首楼消息对象」之类的快照来判定。
2. 当前聊天 id 从宿主的 `getCurrentChatId()` 读。宿主的 `saveChat()` **只能存当前打开的聊天**：
   - 切聊天后再调用，存的是新聊天；
   - 如果宿主当前聊天 id 还指着刚被删的聊天，调用它有可能把那个文件重新写出来。
3. 相关宿主事件：
   - `CHAT_CHANGED`（切换 / 新开聊天）
   - `MESSAGE_DELETED`、`MESSAGE_SWIPED`（删楼、切换回复版本）
   - `CHAT_DELETED`、`GROUP_CHAT_DELETED`（删聊天）
   - `GENERATION_STARTED` / `GENERATION_ENDED` / `GENERATION_STOPPED`（生成开始、结束、停止）

   事件注册集中在 `source/src/presentation/bootstrap/init.ts`（搜 `eventSource.on`）。
4. **本仓库没有宿主源码。**删除「当前正打开的聊天」时：
   - 宿主先发哪个事件、是否自动打开别的聊天或新建聊天、会不会顺手 saveChat，都依赖宿主实现；
   - 凡是结论依赖这些宿主行为的，写明你的假设，至少考虑两种事件顺序，并标「待坐实（需真机）」。
5. TT 基线版本 2.4.0。

### 2.4 三个重点（每条发现都要标明属于哪个重点，与重点无关的标「其他」）

这三类操作都发生在**填表进行到一半**的时候。「进行到一半」包括：

- 自动填表、手动填表、重填（先清掉再填）、一键追平；
- 从规划、清理、发出请求、等 AI 回复，到写入、提交、存盘、收尾的任何一步。

用户还可能把三类操作连着做，例如先删最新楼层，再删除当前聊天，宿主随后新开一个聊天。也可能叠加「终止填表」按钮，或者快速来回切换聊天。

- **A｜删掉最新楼层**：被删的可能正是正在填的那一楼，也可能是它前后的楼。
  - 要看：在途请求会不会中止；迟到的结果会不会被拒收；已经提交的会不会撤掉；表格与剩下的楼层是否一致。
- **B｜删除当前聊天**：在聊天管理里删掉正打开的这个聊天，不先关闭聊天。宿主随后会打开别的聊天或新建聊天。
  - 要看：旧聊天的填表结果会不会写进接下来打开的聊天；我方存盘会不会把已删除的聊天文件重新写出来；向量文件清理与在途的归档谁先谁后。
- **C｜不关闭聊天，直接新开聊天**：对同一角色卡点「开始新聊天」，旧聊天的填表还没结束。宿主复用同一个 chat 数组，见 2.3。
  - 要看：旧轮的结果、标志、定时器、暂存会话、存盘合并窗口、收尾副作用（世界书、向量、回调、剧情推进 / Agent）会不会落到新聊天上；新聊天的填表会不会被旧轮的残留状态卡住。

### 2.5 正确行为的标准（违反任一条即为缺陷）

| 编号 | 不变量 |
|---|---|
| I1 | 旧聊天的填表结果绝不写进新聊天：消息字段、聊天元数据、聊天级配置、世界书、向量文件都不行 |
| I2 | 已删除的聊天不会被我方存盘重新写出文件；它的向量文件会被清理，且不会被在途的归档重新写出来 |
| I3 | 被删除楼层的填表结果不提交；已经提交的会在回滚 / 刷新时撤掉，表格与剩余楼层一致 |
| I4 | 新聊天的自动填表 / 手动填表，不会被旧轮的残留状态卡住或误触发。残留状态包括：标志、终止锁存、定时器、暂存会话、维护锁、存盘合并窗口。被挡住的，最迟在旧轮的兜底时限后恢复 |
| I5 | 不出现未处理的异常、永久挂起的 Promise、泄漏的定时器与监听；提示与实际结果一致，不会失败了还提示成功 |
| I6 | 回到原聊天时，表格按盘上数据正确重建。允许丢掉还没补存的批次（这是已知取舍，见 2.7），但不能留下半截数据 |

## 五、复核阶段（每份分组报告各派一个新的子代理；原样转发本节）

你是**复核者**，任务是**尽力推翻**你拿到的分组报告里的每一条发现。报告作者和你不是同一个人，他的推理可能有错。

### 5.1 你拿到什么

- 一份分组报告文件名（例如 `.analysis-deepseek-review-D02.md`）。
- 第二节「共同规则」全文：硬性约束、宿主事实、场景、不变量、取舍、证据要求同样约束你。

### 5.2 对每一条发现逐项做

1. **重新打开每个引用的 `文件:行号`**，核对引用的代码与实际一致。行号漂移但代码能找到的，记下正确行号。
2. **独立重走触发路径**：从用户操作开始，按代码真实的调用顺序走一遍。重点找报告没提到的守卫：
   - 聊天身份 / 首楼消息快照的复核；
   - 中止信号（AbortSignal、`getChatMutationAbortSignal_ACU`）；
   - 维护锁与事务的版本校验；
   - 「正在填表」标志与终止锁存；
   - 存盘合并的聊天归属判定；
   - 调用方提前 return 的分支。
3. **核对它是不是已知取舍**（2.7），或者是不是以前复审已经登记、已有结论的条目（2.6）。
4. **P0 / P1 必须跑探针测试**（按 2.8 的规定建、跑、删）。
   - 探针做不出来的，必须写明原因，并说明你是靠完整读穿调用链判定的；
   - 只要结论依赖宿主行为，就判「需真机」，不要判「成立」。
5. **P2 / P3 可以只靠读代码判定**，但同样要写出依据。

### 5.3 判定（只能选一个）

| 判定 | 含义 |
|---|---|
| 成立 | 触发路径走得通，后果与报告一致 |
| 降级成立 | 问题存在，但后果比报告轻或触发条件更苛刻。写出新的级别和理由 |
| 不成立 | 有守卫挡住、代码与引用不符、属于已知取舍，或者推理有错。写出决定性证据（`文件:行号` + 代码） |
| 需真机 | 结论取决于宿主行为，jsdom 下无法判定。写出让玩家在酒馆里验证的具体操作步骤（见 5.5） |

**不允许「大概成立」「可能」这类模糊判定。**拿不准的，按「不成立」或「需真机」处理，并写清楚还缺什么。

### 5.4 输出

写进仓库根目录的 **`.analysis-deepseek-verify-Dxx.md`**（与被复核的分组报告同号）：

```
# D02 复核

## 概览
- 原报告：P0 x / P1 x / P2 x / P3 x
- 复核后：成立 x，降级成立 x，不成立 x，需真机 x
- 跑过的探针（已删除）及结果

## 逐条复核

### D02-01 → 成立｜P1
- 行号核对：一致 / 已更正为 xxx
- 重走路径：（简述你自己走的一遍，指出关键的几个点）
- 找过的守卫：（列出查过的守卫，以及为什么挡不住）
- 探针：模拟了什么、关键断言（≤8 行）、结果
- 补充或更正：（原报告的位置、触发条件、修法方向有误时写在这里）

### D02-02 → 不成立
- 决定性证据：`文件:行号` + 代码（≤8 行），说明为什么挡住了
```

写完自查：每个判定都有证据，探针全部删除。

**返回给协调者的最终回复只需要简短一段**：各判定的条数，以及每条的编号和判定。

### 5.5 「需真机」条目的验证步骤写法

玩家没有技术背景，步骤要能照着做：

- 写明在酒馆里点哪里、按什么顺序、在什么时机操作。例如「AI 回复出来、右下角显示正在填表时，立刻……」。
- 写明看什么：表格页的哪张表、哪一行，或者按 F12 后在控制台搜索哪个关键字。
- 写明怎样算正常、怎样算有问题。
