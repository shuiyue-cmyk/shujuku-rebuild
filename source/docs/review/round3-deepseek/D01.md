### D01-01 [P1｜已坐实（探针）｜A、C｜I1 / I3 / I6] 保留层清理在 boundary checkpoint 存盘期间不复核聊天/楼层，按旧下标删掉当前聊天或幸存楼层的表数据

- 位置：
  - `source/src/service/chat/chat-service.ts:1291-1325`（从旧聊天算出 `boundary` / `indicesToPurge`，再 await boundary checkpoint，之后才进入删除循环）
  - `source/src/service/chat/chat-service.ts:1396-1428`（按下标删除字段并 `saveChatToHostStrict_ACU()`）
  - `source/src/service/chat/chat-service.ts:685-737`、`:877-1136`（`ensureV2BoundaryCheckpointForRetainedBufferCore_ACU` / `writeV2BoundaryCheckpointBeforePurge_ACU`，内部有宿主存盘与回放）。
  - 调用方：`source/src/service/table/update-scheduler.ts:456-458`（每轮自动填表在 `refreshData` 之后无条件调用 `purgeOldLayerData`）。
  - 事务守卫：`source/src/service/table/table-write-transaction.ts:444-450`。
- 触发（A）：自动填表刚结束（右下角显示完成/正在收尾）时，保留层清理开始做 boundary checkpoint；它内部调用宿主 `saveChat`（大聊天可能数秒）。这时用户删掉最新楼层：
  1. 宿主从**同一个 chat 数组对象**里 splice 掉楼层；
  2. `purgeOldLayerDataCore_ACU` 里早已算好的 `indicesToPurge` 没有重算；
  3. 存盘返回后，循环用旧下标去删「当前数组」里对应位置的字段，删到的是幸存楼层。
- 触发（C）：同一窗口里用户直接点另一个聊天，宿主清空并复用同一个 `chat` 数组塞入新聊天；循环按旧下标删掉新聊天楼层的表字段，然后 strict save 落盘。
- 现象：新聊天或当前聊天里本来正常的楼层，`TavernDB_ACU_IsolatedData` / 旧版载荷被删掉；表格页缺表/缺行；如果删到新聊天第 0 楼，可能整楼本地表数据丢失。
- 原因（≤8 行）：
  ```ts
  const { indicesToPurge, retainedDataIndices, anchorIndex } = boundary;
  ...
  const checkpointResult = await ensureV2BoundaryCheckpointForRetainedBufferCore_ACU(chat, boundary, { reason: 'purge', save: true });
  ...
  for (const idx of indicesToPurge) {
      const msg = chat[idx];           // 切聊天后 chat 仍指向宿主复用后的新数组
      ...
      delete msg[key];                 // 按下标删到新聊天/幸存楼层
  }
  ...
  await saveChatToHostStrict_ACU();
  ```
- 已排除：
  - `guardChatSwitch` 只在**拿到锁之后**执行一次（`table-write-transaction.ts:444-450`），本函数的关键 await 在事务任务内部，之后没有第二次身份复核；`assertFresh` 只校验表版本，不感知聊天切换。
  - `getChatArray_ACU()` 直接返回 `SillyTavern_API_ACU.chat`（`chat-gateway.ts:19-21`），按宿主事实切聊天复用同一个数组，所以 `chat`/`msg` 不是旧聊天的私有副本。
  - 调用方 `executeAutoUpdatePlan_ACU` 在调用 purge 前没有传 chatKey/回调做复核；`purgeOldLayerData_ACU` 也没有把事务里的 `guardChatSwitch` 语义延伸到内部 await。
  - D05 的 persist 层在落盘前有聊天身份复核，但这里的删除是直接改消息字段 + strict save，不经过 persist 层，拦不住。
- 测试：`source/tests/service/chat/chat-service.test.ts` 的 boundary/purge 用例都是单聊天、不删楼/不切聊天；`source/tests/presentation/chat-mutation-scheduler.test.ts` 只覆盖调度器，不覆盖 purge。没有测试模拟「boundary save 期间宿主替换 chat 数组」。
- 探针（已删除）：`tests/__probe_deepseek__/D01-purge-stale-index.test.ts`。构造 25 层 AI 聊天（第 0 楼带 V2 full frame）、`retainRecentLayers=2`；mock 回放与宿主 strict save，在第一次 strict save 挂起时把同一个 chat 数组清空并填入 26 层新聊天（前 3 层带表数据）、把当前聊天标识改成 `chat-b`，再放行。关键断言：
  ```ts

  expect(h.saveStrict).toHaveBeenCalledTimes(2);
  ```

  结果：通过。旧聊天的 `indicesToPurge=[0]` 精确删掉了新聊天 #0 的表数据；#1 未动，说明不是新聊天自己的保留层清理。
- 修法方向：进入删除循环前用 `getActiveChatStorageIdentity_ACU(chat)` + 首楼消息对象/长度快照复核；更彻底的是给维护事务加「任务内 await 后复核」的通用钩子（照 persist 层 `preparationChatIdentity` 的写法），不能只在拿锁时检查一次。

### D01-02 [P2｜已坐实（探针）｜C｜I4 / I6] 旧聊天的 CHAT_CHANGED 处理器晚排程时，代次守卫会把新聊天的唯一重建链一起取消

- 位置：
  - `source/src/presentation/bootstrap/init.ts:177-221`（`initChainGeneration_ACU` 单槽代次 + running 补跑）
  - `source/src/presentation/bootstrap/init.ts:578-587`（先 `await loadPresetAndCleanCharacterData_ACU()`，之后才 `scheduleInitChainRun_ACU`）
  - 真实慢路径：`source/src/service/runtime/plot-runtime/plot-history-preset.ts:64-84`（旧聊天带 chat 级剧情快照时，迁移分支 `await saveChatToHost_ACU()`）
  - 后果检查：`source/src/service/table/update-scheduler.ts:242-244`（`currentJsonTableData` 为空 → `runtime_not_ready`）
- 触发：
  1. 用户切到聊天 A（A 带旧版 chat 级剧情快照），A 的 `CHAT_CHANGED` handler 开始跑，停在 `loadPresetAndCleanCharacterData_ACU()` 的 `saveChatToHost_ACU()`；
  2. 用户马上切到聊天 B，B 的 handler 很快跑完并在 1200ms 后排出 B 的重建链（代次 N）；
  3. A 的宿主存盘结束，A 的 handler 才排程（代次 N+1），把 B 的排程判为过期；
  4. 1200ms 后 B 的定时器看到代次不符直接放弃；A 的定时器跑 `runChatChangedDelayedRebuild_ACU('chat-a')`，发现当前聊天已是 B，早退。
- 现象：B 没有任何 `loadAllChatMessages` / `refreshMergedDataAndNotify` / snapshot hydrate。`handleChatChangedEvent` 同步段已把 `currentJsonTableData_ACU` 清成 null，于是 B 的表格页空白；之后 B 每轮 AI 回复的自动填表前置检查都会因 `!currentJsonTableData` 报 `runtime_not_ready` 跳过，直到下一次 CHAT_CHANGED 或手动刷新，用户看到的是「新聊天再也不自动填表」。
- 原因（≤8 行）：
  ```ts
  await loadPresetAndCleanCharacterData_ACU();      // A 的慢 await
  ...
  scheduleInitChainRun_ACU(1200, 'CHAT_CHANGED', () => runChatChangedDelayedRebuild_ACU(chatFileName));
  ...
  function scheduleInitChainRun_ACU(delayMs, label, body) {
    initChainGeneration_ACU += 1;                   // 旧聊天后调用也照样递增
    ...
  }
  ```
- 已排除：
  - `handleChatChangedEvent_ACU` 在 await 之后没有核对 `currentChatFileIdentifier_ACU === chatFileName` 再排程；它只依赖 `runChatChangedDelayedRebuild_ACU` 的身份检查，而身份检查只能防止旧链写错，不会为新聊天补一条链。
  - `scheduleInitChainRun_ACU` 的注释假设「后排程者的代次更新」等于「更新的聊天」，本场景正好相反。
  - `initChainRunning` 补跑只在链**正在执行**时登记；这里是定时器还没跑就被新代次取代，不走补跑。
- 测试：`source/tests/presentation/bootstrap/init.test.ts` 覆盖单次 CHAT_CHANGED、启动链中途切聊天（R9-10）和同名聊天连续事件，但没有「两个不同聊天的 handler 交错，旧 handler 晚于新 handler 排程」的用例。
- 探针（已删除）：`tests/__probe_deepseek__/D01-init-chain-starvation.test.ts`。把第一次 `loadPreset` 挂起、第二次立即 resolve，先后触发 `chat-a` / `chat-b` 两个 CHAT_CHANGED，再放行第一次并推进 1200ms。关键断言：
  ```ts
  expect(vi.getTimerCount()).toBe(1);   // 只有 chat-b 的链
  ...
  expect(vi.getTimerCount()).toBe(2);   // chat-a 的旧 handler 也排了程
  await vi.advanceTimersByTimeAsync(1300);
  expect(m.loadMessages).not.toHaveBeenCalled();
  expect(m.refresh).not.toHaveBeenCalled();
  ```
  结果：通过。两次定时器都被取消/早退，聊天 B 没有任何重建。
- 修法方向：排程时捕获聊天身份，当前聊天已不是该身份就不要递增代次（或改为排一条「重建当前聊天」的链）；或者 await 后先比对身份，不一致则丢弃本次排程并确保新聊天已有链。
- 与以前复审的关系：H2/M4 守卫的新问题（不是前两轮已登记条目）。

### D01-03 [P2｜待坐实（需真机）｜B｜I2] CHAT_DELETED 只排向量清理，不中止在途填表/不作废存盘；已删除的聊天可能被我方 saveChat 重新写出

- 位置：
  - `source/src/presentation/bootstrap/init.ts:823-843`（`handleChatDeletedForVectorCleanup_ACU`，唯一的 CHAT_DELETED / GROUP_CHAT_DELETED 监听）
  - 对照：`source/src/presentation/bootstrap/init.ts:544-551`（只有 CHAT_CHANGED 会 `abortOnChatMutation_ACU()` + 清防抖）
  - 存盘侧：`source/src/data/gateways/chat-gateway.ts:119-127`（合并存盘只按聊天 id 作废旧改动）、`:307-344`（strict save 直接调宿主 `saveChat`，没有删除墓碑）
  - 向量侧：`source/src/service/vector/summary-vector-index-chat-deletion-gc.ts:105-119`（目标等于当前聊天、或仍出现在存活名单时跳过清理）
- 触发（顺序一，假设宿主先发 CHAT_DELETED、稍后才切换聊天）：自动填表请求在途或已进入提交/存盘阶段时，用户在聊天管理里删除当前聊天。宿主发 CHAT_DELETED；我们的 handler 只挂一个 5s 后的向量清理，不 abort 在途请求、不取消自动任务、不给存盘合并设墓碑。填表结果回来后继续在旧聊天对象上提交，`saveChatToHostStrict_ACU()` 在宿主 `getCurrentChatId()` 仍指向被删聊天时调用宿主 `saveChat`——按宿主事实 2.3，这可能把刚删掉的聊天文件重新写出来。
- 触发（顺序二，宿主先切到新聊天再发 CHAT_DELETED）：`abortOnChatMutation` 已中止请求，但如果此刻已有一条 strict save / 合并补存排进宿主队列，宿主仍可能在删除落盘之后执行它；之后 5s 的向量清理看到文件又存活或仍是当前聊天，就跳过，留下孤儿向量。
- 现象：已删除的聊天文件复活；或它的向量外置文件永远留着（要等下次启动 60s 后的孤儿清扫）。两种情况都违反 I2。
- 原因（≤8 行）：
  ```ts
  const handleChatDeletedForVectorCleanup_ACU = (deletedChatName: unknown): void => {
    const name = String(deletedChatName || '').trim();
    if (!name) return;
    setTimeout(() => {
      void cleanupSummaryVectorIndexForDeletedChat_ACU(name).catch(...);
    }, 5000);
  };
  ```
- 已排除：
  - `abortOnChatMutation_ACU` 的唯一调用点是 `handleChatChangedEvent_ACU`（grep 全仓），CHAT_DELETED / GROUP_CHAT_DELETED 没有其它监听或中止逻辑。
  - 存盘合并的归属判定只在「当前聊天 id 与新聊天不同」时作废旧改动（`chat-gateway.ts:120-127`）；被删聊天仍是 current 时 key 相同，会正常补存。
  - strict save 没有任何「聊天已删除」的全局墓碑（`chat-gateway.ts:307-344` 只做 pagehide 判断后直接 `saveChat`），宿主保存队列的行为也无法从本仓库判断。
  - 向量清理自己的 fail-safe（目标即当前聊天 / 同名存活 / 枚举失败一律跳过）会放大这个问题，但它属于 D06，见跨组线索。
- 测试：`source/tests/presentation/bootstrap/init.test.ts` 只断言 CHAT_DELETED handler 注册；`source/tests/service/vector/summary-vector-index-chat-deletion-gc.test.ts:65-68` 把「被删聊天等于当前聊天时跳过」当成预期，没有覆盖「删完还来不及切换」的顺序。
- 修法方向：CHAT_DELETED 若指向当前聊天，立即 `abortOnChatMutation_ACU()` + `cancelPendingAutoTasks_ACU` + 通知 gateway 设置「已删除聊天」墓碑，阻止 strict/coalesced save 直到 CHAT_CHANGED 清墓碑；向量清理改到墓碑/切换之后执行。
- 与以前复审的关系：新问题（前两轮没有把「删聊天 + 在途存盘」一起审）。

## 设计层面的疑虑（不计入缺陷）

- 删楼后 1.2s 内切聊天：`cancelPendingChatMutationRefresh_ACU`（`chat-mutation-scheduler.ts:73-80`）直接把 `pendingDeletion` 清掉，删楼当轮的 checkpoint 前移恢复不会为旧聊天执行。R9-03 修的是「不把删楼标记带到新聊天」，但如果被删的最新楼携带唯一回放根 / 休眠表快照，回到原聊天时冷回放可能报无根或丢表。建议改成按聊天保存待恢复队列，回到该聊天时补跑。
- `resetScriptStateForNewChat_ACU` 不直接复位 `isAutoUpdatingCard_ACU` / `tableFillStopLatched_ACU`，完全依赖旧轮 finally 清标志；聊天切换没有像「终止填表」那样的 30s 强制放开兜底。正常 abort 路径能收尾，但旧轮若卡在不可中止的宿主调用上，新聊天会一直等。
- init 重建链互斥没有超时；`runChatChangedDelayedRebuild_ACU` 里 await 的向量预加载/重建若长期不返回，后续所有聊天的重建只能排队等它结束。
- `checkpoint-delete-guard` 会把被删楼层携带的 full / per-sheet checkpoint 前移到幸存楼层（模块头有说明）。这保证回放链不断，但被删最新楼的 per-sheet 结果可能继续留在表里，和 I3「删楼=撤销该楼编辑」有张力；本次按已知取舍不计数。

- CHAT_CHANGED 同步段：`abortOnChatMutation_ACU`、`clearAutoFillDebounce_ACU`、清派生缓存、`cancelPendingChatMutationRefresh_ACU`、延迟链的聊天身份/epoch 复检（`init.ts:544-587`、`381-401`、`420-434`）逻辑完整；失败有 `recoverDelayedRebuildFailure_ACU`。
