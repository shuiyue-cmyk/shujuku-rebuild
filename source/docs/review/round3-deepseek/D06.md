### D06-01 [P1｜已坐实｜B/C｜I1] 手动重填收尾的向量「剩余行发布」不含来源聊天身份：切聊天后旧聊天的 summary 行会发布进新聊天的向量镜像

- 位置：

- 触发：前提是旧聊天已有纪要向量镜像（交火索引开启且归档过）。做一次手动重填（勾选纪要表，确认后进入清理），在清理/建模板临时根/`reloadStorageProvider` 这段异步窗口里切换聊天（B 或 C）——这是发布路径；或者更晚，在最终快照提交（`:6038-6047`）期间切聊天——这是随后的 `manual_refill_complete` 重建路径。如果新聊天是旧聊天的分支/复制聊天（或任何 full checkpoint 数据指纹相同、且存在纪要表的聊天），发布端的 `expectedBaseFingerprint` 校验会通过。
- 现象：`publishManualRefillSummaryVectors_ACU` 在发布后检查（`:5759`）之前执行；发布把旧聊天 A 的 summary 行、旧 pack 引用写进新聊天 B 的 `summaryVectorIndexFrame`，并先删掉 B 自己所有镜像帧（`collectSummaryVectorMirrorFrameRefs_ACU` + `undo.remove`）。如果切聊天发生在清理之后（本条的发布窗口），A 自己的镜像已被清理掉而又没有发布回去，回到 A 时索引也不完整。之后 B 的召回会读回 A 的纪要内容。最终 `executionSnapshot` 复核只阻止了后续 AI 调用，无法撤回已发布的数据；`:6054` 的 `manual_refill_complete` 重建则直接以当前聊天/当前运行时跑 `rebuild_repair`，同样没有来源聊天校验。
- 原因：
  ```ts
  const snapshot = { kind:'ready', sourceTableKey, rows, packRefs, expectedBaseFingerprint };
  // ...切聊天...
  const scope = normalizeSummaryVectorIndexScope_ACU({
      chatKey: currentChatFileIdentifier_ACU,   // 发布时才取，已经是新聊天
      isolationKey, sourceTableKey: snapshot.sourceTableKey,
  });
  ```
  发布函数没有来源聊天字段，调用方又在最后一个身份复核之后隔了清理/建根/reload 多个 await 才发布；`executionSnapshotContextStillMatches_ACU` 在 `:5568`（清理前）与 `:5759`（发布后）之间没有任何一次调用，挡不住发布窗口里的切聊。
- 已排除：
  - `grep executionSnapshotContextStillMatches_ACU` 共 12 处调用；手动重填清理后到发布前没有复核（`:5656-5714` 区间）。
  - `publishSummaryVectorMirrorRowRemovalSnapshot_ACU` 只校验 `expectedBaseFingerprint`（`:344-354`），该指纹只证明“表格内容相同”，不证明“还是同一个聊天”；且 manifest 在指纹校验之前就上传（`:296-318`）。

### D06-03 [P2｜已坐实（代码路径；宿主事件顺序待真机）｜B｜I2] 删除当前聊天的向量清理是一次性尽力清理：最新文件必被 10 分钟 grace 保留，当前聊天守卫还可能整体跳过，且没有针对该聊天的重试

  - `source/src/service/vector/summary-vector-mirror-writer.ts:530-537`（代次校验）、`:611`（写帧后 `saveChatToHostStrict_ACU`）、`:634`（事务成功后才 `finalizeSummaryVectorMirrorFiles`）。
  - 对照：flush 队列自己的失效入口 `summary-vector-index-flush-queue.ts:640-652` 会拿 scope 锁并写 `invalidated` 墓碑；删聊天清理走的是无锁的 delete 版本。
- 触发与两种事件顺序（宿主实现未知）：
  1. 假设 CHAT_DELETED 先到、CHAT_CHANGED 尚未到（或宿主不自动打开别的聊天）：+5s 时 `currentChatFileIdentifier_ACU` 仍等于被删聊天名 → `:105-108` 整体跳过；此后没有任何重试。
  2. 假设 CHAT_CHANGED 已经先到：进入 Safe GC，但被删聊天最近一次填表刚生成的 pack/manifest 一定在 10 分钟内 → 被 grace 保留；在途 flush 若已通过 `:535` 的代次校验，清理删任务也拦不住它继续 `:611` save / `:634` finalize，文件会在清理之后变成 published 孤儿。
  3. 若删除期间正在 `forceFlushChatSave`（填表 finally），`keepChatSaveDirtyIfSameChat_ACU` 把 `currentChatSaveKey === null` 当同聊天（`chat-gateway.ts:120-128`），还可能继续调用宿主 `saveChat()` 把已删文件重新写出来（见跨组线索）。
- 现象：删除一个刚填过表、刚生成过向量索引的聊天后，最新的向量 pack/manifest 仍留在外部存储和 registry；在长会话里可能一直留到下一次启动（且启动清扫受 24h 节流）。这违反 I2“它的向量文件会被清理，且不会被在途的归档重新写出来”。
- 原因：
  ```ts
  if (chatKey === getCurrentChatKey_ACU()) return { performed:false, reason:'target_is_current_chat', ... };
  ...
  if (Date.now() - registeredAt < SAFE_GC_GRACE_PERIOD) { retainedPaths.push(path); continue; }
  ```
  清理只发一次、没有“被删聊天”墓碑；Safe GC 的 grace 与 prepared 保护是为普通并发写的，对“已确认删除”的 scope 过强；清理也不等待/取消正在执行的 flush runner。
- 已排除：
  - `grep cleanupSummaryVectorIndexForDeletedChat_ACU|sweepOrphanSummaryVectorIndexFiles_ACU` 只有 init.ts 两处调用；删除路径没有第二次尝试。
  - `cleanupUnreachableSummaryVectorIndexFiles_ACU` 没有“已删除 scope 跳过 grace”的选项（`summary-vector-index-types.ts:469-472` 只有 scopeHints）。
  - 同名存活守卫本身是必要的（跨角色同名共享 scope），问题不在它；问题在当前聊天守卫与一次性语义。
  - `DELETE / CHAT_DELETED` 的 payload 形状与宿主切换时序未真机验证。
- 测试：`tests/service/vector/summary-vector-index-chat-deletion-gc.test.ts` 把 `cleanupUnreachableSummaryVectorIndexFiles_ACU` 整个 mock 掉，只断言“被调用/没被调用”，没有真实 grace、没有在途 runner、没有“当前聊天”两种事件顺序；flush 队列测试只覆盖切聊跳票，不覆盖删聊天。
- 修法方向：删聊天时写一个按 chatKey 的删除墓碑（带时间），让 enqueue/restore/flush 都拒绝该 scope；清理改成“先立即清 IDB/任务，再按 grace 到期时间重试文件回收”，或在 Safe GC 增加“已确认删除的 scope 可跳过 grace”的专用入口；对正在跑的 flush，等待其 settle 或让其 finalize 后二次扫一遍。
- 与以前复审的关系：新问题。R5-04 是“GC 可达性只看当前聊天导致分支/改名聊天被回收”（已决定不修）；本条是“删聊天清理清不到最新文件/被跳过后无重试”，方向相反。

## 设计层面的疑虑（不计入缺陷）

1. **R5-04 的可达性口径在“切聊天后 retention GC”上更激进**：`runScopedRetentionGcAfterFlush_ACU` 在 flush 成功后用任务 scope 调 Safe GC，而 `collectSummaryVectorIndexReachability_ACU` 只遍历当前打开的聊天。如果 flush 提交成功后用户立刻切走，旧聊天仍在磁盘上引用这些文件，却可能被当成不可达在 grace 后回收。R5-04 已按产品决定“不修”，这里只记录它也会作用于普通切聊天，不只是分支/改名。
2. **删聊天的“当前聊天”守卫**：`cleanupSummaryVectorIndexForDeletedChat_ACU:105-108` 的注释假设“删除事件不应指向当前打开的聊天”，但本组重点 B 恰好就是删除当前聊天。5s 延迟只是启发式，不是不变量；建议改成“删除事件的名字 === 刚离开的聊天”时也允许清理，并对无法确认的情况安排延迟重试。
3. **10 分钟 grace 与事件驱动清理的目标冲突**：模块头注释承诺“聊天被删除后其向量文件/IDB 缓存/flush 任务成为永久孤儿 → 事件驱动即时清理”，但 Safe GC 的 grace/prepared 保护会让最新文件在删除时必被保留；如果产品坚持 grace，建议明确写成“即时清 IDB，文件延迟到启动清扫”，避免后续维护者误判。
