## 发现

### D04-01 [P2｜已坐实｜其他｜I3] AI 的 SQL 可以改 `row_id`：行锁补偿把被改号的行整行插回，表格里出现重复行

- **位置**：
  - `source/src/service/table/sql-table-service.ts:1052-1070`（`materializeSystemRowIdsForSqlInserts_ACU`：只处理 INSERT；REPLACE 与所有非 INSERT 原样放行）
  - `source/src/service/table/sql-table-service.ts:1170-1233`（`assertNoHiddenPhysicalColumnMutations_ACU`：只检查隐藏物理列，不检查 `row_id`）
  - `source/src/service/table/table-lock-enforcement.ts:114-124`（按前像 rowId 判断「行被删」）
  - `source/src/service/table/table-lock-enforcement.ts:183-193`（整行 INSERT 补偿）
  - `source/src/service/table/table-update-commit.ts:163-194`（`assertPersistableRowIdentities_ACU` 只查空/重复，不查身份是否被改写）
- **触发**：用户给某行加了行锁（可视化编辑器的锁，写入 `settings_ACU.tableUpdateLocks`）；自动/手动填表时 AI 输出 `UPDATE 表 SET row_id = 新值, 业务列 = ... WHERE row_id = 旧值;`。默认填表提示词只禁止「INSERT 包含 row_id」（`source/src/shared/table-defaults/fill-prompt.js` 的 UPDATE 段没有任何 row_id 禁令），模型完全可能写出这种语句。
- **现象**：锁定行的业务列修改会被回滚（正确），但**该行会以旧 `row_id` 被整行插回**，改号后的副本继续存在——同一业务行变成两行；其中一行带着这次应被锁挡住的修改。无锁时更安静：`row_id` 被直接改写，旧 `row_id` 上的行锁与任何外部引用全部失效，没有任何提示。
- **原因**：
  ```ts
  // sql-table-service.ts:1068-1069
  if (isSqlMutationKeyword_ACU(action, 'REPLACE')) return statement;
  if (!isSqlMutationKeyword_ACU(action, 'INSERT')) return statement;
  ```
  UPDATE 不走 row_id 物化，也不会被拒绝；隐藏列守卫的 `hidden` 集合不包含 `row_id`（`:1212`）。锁补偿看到「前像 rowId 1 不在后像」，按 DELETE 处理，追加 `INSERT INTO ... (row_id, ...) VALUES ('1', 原值)`（`table-lock-enforcement.ts:183-193`），于是前后两行并存。commit 的身份断言只要求非空、不重复（`table-update-commit.ts:178-192`），能通过。
- **已排除**：grep 了 `applyEditsWithSystemRowIds` 的全部调用点（`update-orchestrator.ts:2106`、`:3550`；`table-fill-staging-session.ts:103`）与 `assertNoHiddenPhysicalColumnMutations_ACU` 的全部调用点（`update-orchestrator.ts:1656`、`sql-table-service.ts:1155-1162`、`:1942`），上游没有任何 row_id 护栏；`rebindSqlMutationIdentifiers_ACU` 只重绑表名/列名；R9-05 只修了 CRUD 的 row_id 改写，AI SQL 路径没覆盖。锁补偿的「整行恢复」对 DELETE 是正确的，问题在于把「改号」也当成「删除」。
- **测试**：`tests/service/table/sql-table-service.test.ts` 的「锁定差异回滚（S0-2）」只覆盖 `UPDATE 业务列` 和 `DELETE`，没有覆盖改 `row_id`；`table-edit-parser.test.ts` 把 SQL 分支 mock 掉了。探针（见文末）在快照路径与 live provider 路径都复现。
- **修法方向**：在唯一执行边界（`materializeSystemRowIdsForSqlInserts_ACU` 或 `applyEditsWithSystemRowIds`）拒绝 `UPDATE ... SET row_id = ...`（含 `INSERT ... ON CONFLICT DO UPDATE SET row_id`）；或者让锁补偿按「业务行内容」而不是仅按 rowId 判删除，但更简单的是保持 row_id 不可写。REPLACE 的显式 row_id 是提示词里的既定约定，可保留。
- **与以前复审的关系**：新问题；与 R9-05（CRUD 可改写 row_id，已修）同族，AI SQL 路径未覆盖。

  - 我查了 `isTableFillStopRequested_ACU` 与 30s 强制放开（`state-manager.ts:677-694`）：那是用户点「终止」的兜底，不会在切聊天时触发。

### D04-03 [P3｜已坐实｜其他｜I5] 原生工具模式：正文里的 `<tableEdit>` 遇到 `table_sql` 空 `sql` 会被静默丢弃，并按「零操作成功」提交

- **位置**：`source/src/service/ai/prompt-builder/table-fill-tools.ts:119-143`；调用点 `prompt-api-call.ts:274-289`；零操作语义 `update-orchestrator.ts:1647-1651`、`table-edit-parser.ts:147-152`。
- **触发**：设置里开启「填表原生工具调用」（默认关闭）且非流式；AI 在正文写了一个完整的 `<tableEdit>...SQL...</tableEdit>`，同时调用 `table_sql({"sql":""})`（例如把工具调用当「提交」、正文当「内容」）。
- **现象**：`calls` 存在但 `parts` 为空，`content.replace(/<tableEdit>[\s\S]*?<\/tableEdit>/gi, '')` 把正文块剥离（`:140`），最终返回 `<tableEdit>\n\n</tableEdit>`（`:141-142`）。编排层看到标签齐全、块内为空，按零操作提交；楼层仍被记为已填，正文里的修改永远不落表，界面提示成功。
- **原因**：
  ```ts
  const residual = content.replace(/<tableEdit>[\s\S]*?<\/tableEdit>/gi, '').trim();
  const block = `<tableEdit>\n${parts.join('\n')}\n</tableEdit>`;
  return { ok: true, text: residual ? `${residual}\n${block}` : block, viaTool: true };
  ```
- **已排除**：工具调用里 `sql` 非空时（即使正文也有块），探针确认正文块会被正确剔除、工具结果保留（符合预期）；只有「所有工具调用都为空 + 正文有非空块」这一种组合会吞改动。`shouldUseTableFillNativeTools_ACU` 只在开启且非流式时挂工具，流式走正文路径，不受影响。
- **测试**：`tests/service/ai/table-fill-tools.test.ts` 只覆盖正常工具调用/非法 JSON/空内容，没有覆盖「空 sql + 正文块」。
- **修法方向**：当所有 `table_sql` 的 `sql` 都为空、而正文存在非空 `<tableEdit>` 时，以正文为准（或返回 `ok:false` 让编排层重试），不要静默生成空块。
- **与以前复审的关系**：新问题。

## 跨组线索

1. **SQL 模式不遵守「仅识别最后一对 `<tableEdit>`」**（根因 D02）：`update-orchestrator.ts:1647-1651` 用 `/tableEdit>([\s\S]*?)<\/tableEdit>/i` 取**第一个**块，而 `table-edit-parser.ts:55-75` 的默认是取**最后一对**（`settings_ACU.tableEditLastPairOnly`，UI 文案 `presentation-v3/pages/TablePage.vue:91`「仅识别最后一对…忽略前面思维链或草稿里的旧指令」）。后果：模型先写草稿块再写正式 SQL 时，执行的是草稿；草稿块为空、正式 SQL 在后时，`isSqlContent(tableEditText)` 为 false，随后 DSL 解析拿到真正的 SQL 并抛出「SQLite SQL tableEdit must be applied through table update commit model」（`table-edit-parser.ts:154-159`），整轮直接失败且不会按 model 错误重试。建议 SQL 提取也走 `extractTableEditInner_ACU`（或至少遵守 last-pair 设置）。
2. **staging 组共用一个 AbortController，删一个楼会中止同批所有组**（根因 D02/D01）：`settings-ui-trigger.ts:244` 建一个 `autoGroupedAbortController`，`:261-267` 传给整个 staging run；`update-orchestrator.ts:2893-2896`/`:2942-2945` 给 bucket 里每个 job 传同一个控制器；`table-fill-target-watch.ts:30-43` 对任一失效目标直接 `controller.abort()`。于是同 bucket 里目标仍然有效的组也被中止，`:2907-2927` 把整 bucket 记为失败。普通组每次 `proceedWithCardUpdate_ACU` 都新建控制器（`presentation/triggers/update-process.ts:220`），不受影响。与 2.7 的「只中止目标楼层已失效的那些请求」不符。
3. **自动填表计划没有绑定聊天快照**（根因 D02，窗口较小，待真机）：自动入口在 `settings-ui-connect.ts:368-395` 已有一道 `currentChatFileIdentifier_ACU !== scheduledChatKey_ACU` 复检，但复检之后到 `processUpdatesBatch` 取 `chatHistory` 之间还有 `executeAutoUpdatePlan` / 存储迁移 / runtime-only flush 等 await；`settings-ui-trigger.ts:139-190` 生成计划时没有把 chatKey 随计划带下去，`update-orchestrator.ts:3985` 的 `const chatHistory = getChatArray_ACU()` 是现取的（ST 切聊天复用同一数组），`:4047` 用它切片；`executeCardUpdateCore_ACU` 到 `:3381` 才 `captureFillExecutionScope_ACU()`，这时捕获到的已经是新聊天的 chatKey/targetGuard；commit 的 chatKey 只与 `currentChatFileIdentifier_ACU` 比（`table-update-commit.ts:313-323`）。若 CHAT_CHANGED 恰好落在复检之后、取 chatHistory 之前，旧下标会套到新聊天上；新聊天足够长时会按新聊天消息填表并把帧写进新聊天楼层（I4/I1 风险）。需要真机确认宿主事件顺序；另：如果宿主不派发 CHAT_CHANGED 就换了聊天，commit 的镜像（只由 resetScriptState 更新）也察觉不到。
4. **中止登记时机**（D04-02 的根因）：`prompt-api-call.ts:84` 才 `trackAbortController_ACU`，`state-manager.ts:613-643` 只中止已登记的控制器；prepare 阶段不在保护范围内。D01/D02 调整 CHAT_CHANGED 中止覆盖面时，建议把「一次填表」的控制器在 prepare 前登记，或给 prepare 传入 chat mutation signal。

## 设计层面的疑虑（不计入缺陷）

- **填表请求没有传输超时/空闲看门狗**：`api-call.ts:643-659` 的 `postChatCompletion_ACU` 明确不设硬超时（长生成合法），填表也走这个出口；服务商半开连接时 fill promise 永久挂起，`isAutoUpdatingCard_ACU` 一直为 true，直到用户点「终止」（30s 后只强制放开标志，promise 仍悬挂）。建议给填表单独加「等响应头/相邻块」的空闲超时（照 `callAIWithResolvedPreset_ACU` 的 120s 空闲口径），不要把长生成和挂死混为一谈。
- **`fixNumericKeysLayer_ACU` 不区分字符串内外**（`json-sanitizer.ts:266-269`）：探针里 `{"0":"时间, 5: 清晨",}` 被改成非法 JSON `{"0":"时间, "5": 清晨"}`；目前下游 `coerceLooseRowObject_ACU` 恰好把文本还原，所以没有用户可见危害，但只是「下一层兜住了」，再加一层清洗就可能改坏单元格。建议和其他清洗层一样做 in-string 感知。
- **`prepareAIInput_ACU` 的 `{[db...]}`/`<if>` 读的是 live runtime**（`prompt-api-call.ts:235-247`），不是本 bucket 的 `job.baseSnapshot`；`$1` 与 `$0` 是冻结的，条件/模板变量却会看到运行时后续批次的数据。正常路径下这是为了让重试看到最新基底，但对历史桶（追平）会造成 prompt 内部不一致（R2A-09 的同族取舍，未升级为缺陷）。

## 查过但判定没问题的场景

- **流式/非流式响应解析**：`prompt-api-call.ts:437-539` 对 OpenAI `[DONE]`、`finish_reason`、Anthropic `message_stop`、Responses `response.completed`、Gemini `finishReason`、Interactions `interaction.completed` 都有结束判定；无结束信号按截断返回 null（R8-07/R8-02 修复在位）。`AbortError` 在 `parseNonStreamResponse`/`parseStreamResponse`/`postChatCompletionTurn` 都原样重抛，不会被降级成可重试的模型错误。
- **迟到回复**：`collectGroupFillResponseCore` 在 prepare 后、AI 返回后、重试等待后都复查 `isStopped()`（`update-orchestrator.ts:1510`、`:1605`、`:1635`、`:1698`）；目标失效的请求由 `watchTableFillTarget_ACU` 当场 abort，返回后 `collectGroupFillResponse_ACU:1489` 再把 `aborted` 改判为 `staleResult`。commit 又有 chatKey + targetGuard 双检（`table-update-commit.ts:302-323`、`:444`）。

- **row_id 分配**：`buildRowIdReservationsByRuntimeTable_ACU` + `allocateStableRowId_ACU` 按整表现有 row_id 求最大并即时预留，批内多行不会碰撞；INSERT 显式带 row_id 的物化语义（业务列重排）正确。
- **切聊天后的盘上重建**：`loadOrCreateJsonTableFromChatHistory_ACU`（`table-service.ts:396-404`）用 chat 数组 + chat id + isolation key 复核；`reloadStorageProvider`/`hydrateStorageProviderFromSnapshot_ACU` 有 lifecycle epoch 与身份预检/复检（`table-storage-strategy.ts:321-323`、`:392-400`）。本组没有找到能把旧聊天数据持久化进新聊天的路径（与 R9-10 的既有修复一致）。

- **direct-send**：五种协议的请求组装、非流式归一（`normalizeDirectProviderReply_ACU`）、`signal` 透传与 `redirect: 'error'` 都正确；错误体由调用方脱敏后展示。

- **`table-fill-tools` 非空 sql 场景**：工具结果优先、正文残留块剔除；仅在「空 sql + 正文块」组合吞改动（D04-03）。
