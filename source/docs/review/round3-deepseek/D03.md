## 发现

### D03-01 [P0｜已坐实｜B/C｜I1、I6] 重填「零提交回滚」按当前聊天执行：切聊天后旧聊天的清理永不回滚，重填范围内的旧数据永久丢失；新聊天楼层身份相同还会被写入旧快照

- 位置：
  - `source/src/service/table/update-orchestrator.ts:5267-5292`（`rollbackRefillCleanupOnZeroCommit`，只拿 handle 调用回滚，没有聊天身份参数）
  - `source/src/service/table/update-orchestrator.ts:5297-5321`（`failManualRefillSession`，回滚后按“当前聊天”重载/刷新）
  - `source/src/service/table/update-orchestrator.ts:5758-5763`、`5867-5881`（检测到切聊天后走 `failManualRefillSession`）
  - `source/src/service/chat/chat-service.ts:2931-2988`（`rollbackManualRefillRangeSnapshotAtomic_ACU` 在**调用时**读取 `getChatArray_ACU()` 与当前 isolationKey）
  - `source/src/service/chat/chat-service.ts:2885-2888`（交回的回滚句柄只有 `entries` 与 `sheetKeys`，没有 chatKey）
  - `source/src/service/table/table-write-transaction.ts:438-449`（`guardChatSwitch` 只在事务入口把“当前 chatKey”与自身比较；回滚事务在切换之后才开始，因此必然通过）
- 触发：手动填表（重填，`clearBeforeUpdate:true`）确认后，清理已经严格保存到聊天 A；AI 请求在途（进度提示「调用 AI」）时，在聊天列表里点开聊天 B（同一角色新聊天或另一个已有聊天都可以）。也可以是在清理后的准备阶段直接删除当前聊天 A，宿主随后新开聊天。
- 现象：
  - 聊天 A 的选中表在重填范围内的 checkpoint/增量已被 `clearManualRefillSheetDataInRange_ACU` 删除并 `saveChatToHostStrict_ACU` 落盘；切走后执行失败，`failManualRefillSession` 调用的回滚却按聊天 B 执行。聊天 A 永远收不到回滚，返回聊天 A 时看到的是清理后的半截状态（若被删的是唯一基线，旧数据不可恢复）。
  - 若聊天 B 的楼层在回滚句柄对应下标上身份指纹相同（正文兜底形态：无 `send_date`/`gen_id`/稳定 id，`mes` 相同），回滚会把聊天 A 的清理前快照写进聊天 B 的楼层。探针已直接复现。
  - 同一根因还有两个更窄的写点（未单独编号）：`establishManualRefillTemplateRoot_ACU`（`update-orchestrator.ts:5682-5696`）和最终快照 `commitManualRefillSheetSnapshotInRangeAtomic_ACU`（`update-orchestrator.ts:6042-6048`，该函数在 `chat-service.ts:2519-2526` 同样只有入口 `guardChatSwitch`、没有原始 chatKey）。最后一个 chunk 的聊天身份复检（`5867`）之后、最终提交之前没有再次核对，`5998` 的 `loadAllChatMessages_ACU` 是异步窗口。
- 原因（关键代码）：
  ```ts
  // chat-service.ts:2936
  const chat = getChatArray_ACU();
  // ...按 entry.index 在 chat 上恢复...
  // table-write-transaction.ts:438-449
  const chatKey = normalizeScopePart_ACU(options.chatKey ?? currentChatFileIdentifier_ACU, 'current-chat');
  if (options.guardChatSwitch && options.chatKey === undefined) {
      const currentChatKey = normalizeScopePart_ACU(currentChatFileIdentifier_ACU, 'current-chat');
      if (currentChatKey !== chatKey) throw new TableWriteChatSwitchedError_ACU(...);
  }
  ```
  回滚事务没有传 `chatKey`，`chatKey` 就是“切换后的当前聊天”，入口校验自然相等；句柄本身也不带聊天身份，无法判断快照属于哪个聊天。
- 已排除：
  - `executionSnapshotContextStillMatches_ACU`（`update-orchestrator.ts:4295-4300`）只在清理前/AI 前/chunk 前检查，失败路径进入回滚时已经切换，检查只会把流程导向回滚，不会阻止回滚写新聊天。
  - `clearManualRefillSheetDataInRange_ACU` 的 `guardChatSwitch`（`chat-service.ts:2916`）只保护清理事务本身，不保护之后的回滚。
  - `rollbackManualRefillRangeSnapshotAtomic_ACU` 的逐条身份指纹校验只防止“把快照写到错误楼层”，不防止“在错误的聊天里找同身份楼层”；指纹相同就照写。
  - 查过调用方：`rollbackRefillCleanupOnZeroCommit`、`failManualRefillSession` 均只被 `orchestrateManualUpdate_ACU` 内部调用（`grep` 确认无第二个调用者），无上层兜底。
- 测试：
  - `source/tests/service/chat/chat-service.test.ts` 的「聊天在重填期间被改动时按身份跳过错位楼层」等用例只演示**同一个 chat 数组内**的删楼/滑动，没有切聊天；`currentChatFileIdentifier_ACU` 在该测试里是常量 `'chat-test'`，无法构造切换。
  - `source/tests/service/table/update-orchestrator.test.ts` 把 `rollbackManualRefillRangeSnapshotAtomic_ACU` mock 成 `vi.fn()`，只断言“是否调用/传了什么 handle”，看不到回滚作用到哪个聊天。
- 探针（已删除）：`tests/__probe_deepseek__/D03-refill-rollback-chat-switch.test.ts`。模拟：聊天 A 上执行真实的 `clearManualRefillSheetDataInRange_ACU` 拿到 handle；把 `getChatArray_ACU()` 与 `currentChatFileIdentifier_ACU` 换成聊天 B；调用真实的 `rollbackManualRefillRangeSnapshotAtomic_ACU`。关键断言与结果：
  ```ts
  expect(rollback.success).toBe(true);
  expect(chatB[0].TavernDB_ACU_IsolatedData?.['']?.storageFrame?.checkpoint?.data?.sheet_1)
    .toEqual({ name: '纪要表', content: [['row_id','事件'],['r1','旧数据']] });
  expect(chatA[0].TavernDB_ACU_IsolatedData?.['']?.storageFrame?.checkpoint?.data?.sheet_1).toBeUndefined();
  // 第二例（B 的 send_date 不同）：success=false、skippedIndexes=[0]，A 仍不恢复
  ```
  两个用例均通过：同一身份时旧快照写进 B；不同身份时 B 全部跳过、A 仍保持清理态——两条路径的共同结果是聊天 A 的清理永不回滚。
  探针把 `runTableWriteTransaction_ACU` mock 成直通任务，只隔离锁/事务外壳；被测的 `rollbackManualRefillRangeSnapshotAtomic_ACU` 的聊天查找、指纹校验、快照恢复与 strict save 都是真实代码。真实事务“`chatKey` 缺省 = 当前聊天”的行为已在 `table-write-transaction.ts:438-449` 核对——切换后新开的事务必然自比通过。
- 修法方向：清理时把 `chatKey`（以及首楼消息身份）写进回滚句柄；回滚前若当前 chatKey 不等于句柄 chatKey，禁止任何写入，改为把快照作为“待回滚日志”按 chatKey 持久化（回到该聊天时再恢复/提示），或至少在 CHAT_CHANGED 同步段保存旧聊天引用后再回滚。最终快照提交也必须接收并校验原始 chatKey。
- 与以前复审的关系：R3-06 修复的是“同一聊天内零提交回滚会留下双根”，本条是它没有覆盖的跨聊天情形；不是回归，是同一安全设计在切换聊天边界上的缺口。

### D03-02 [P1｜待坐实｜C｜I1] 追平终态进度写入不绑定聊天身份：切到另一个聊天后，旧计划的 `manualRefillProgress` 可能写进新聊天

- 位置：
  - `source/src/service/table/update-orchestrator.ts:4650-4659`（`resolveSafeTerminalTargetMessageIndex` 用**当前** chat/isolationKey 找锚点）
  - `source/src/service/table/update-orchestrator.ts:4721-4759`（`persistCatchUpTerminalProgress` 的 `runTableUpdateCommit_ACU` 调用没有 `chatKey`）
  - `source/src/service/table/table-update-commit.ts:313-323`（`chatKey` 缺省时把当前值当期望值，检查恒通过）
  - `source/src/service/table/update-orchestrator.ts:4822、4867、4898、4985、5055、5082、5118`（各失败/停止/成功终态都会调用）
- 触发：一键追平已经提交完若干 bucket，进入 `verifyCommittedCatchUpReplay`（大聊天回放可能持续数秒）或最后的 `refreshData`（世界书合并）期间，用户切到同一角色的另一个已有聊天（该聊天在旧计划的目标下标处恰好是 AI 楼层，且之前已有 full/transition checkpoint）。终态写入随后在“当前聊天”执行；是否真的落帧取决于新聊天的运行时数据与锚点是否就绪。
- 现象：
  - 新聊天对应楼层被写入一帧 `manualRefillProgress`（旧 runId、旧 `selectedSheetKeys`、旧 `completedSheetMessageIndexByKey`、旧 targetAiFloor）。这是聊天级/帧级元数据，不是新聊天自己的追平记录。
  - 该帧会被存储策略判为“有数据”（`storage-strategy-resolver.ts:41`、`table-v2-recovery-service.ts:93/101/123` 都把 `manualRefillProgress` 当作数据证据），可能改变新聊天的 mixed-storage/恢复分类；后续恢复计划看到的是一段不属于它的进度。
  - 如果新聊天没有对应 AI 楼层/锚点，或 delayed rebuild 未完成导致 `currentJsonTableData_ACU` 为 null，写入会失败并只把错误拼进旧 run 的 `result.error`；用户在新聊天看到“进度记录没保存成功”之类与己无关的提示，或根本不知道旧聊天少写了终态。
- 原因（关键代码）：
  ```ts
  const progress = buildCatchUpProgress(status, lastError);
  const commitResult = await runTableUpdateCommit_ACU({
      source: 'manual_fill',
      reason: `orchestrateManualCatchUp:terminal:${status}`,
      isolationKey,                    // 当前 isolationKey
      writeSet: buildWriteSetForSheetKeys_ACU(selectedSheetKeys, currentJsonTableData_ACU),
      initialData: currentJsonTableData_ACU,
      targetMessageIndex: safeTargetMessageIndex, // 由当前 chat 解析
      ...
      strictSave: true,
  }, ...);
  ```
  没有 `chatKey`；`assertExpectedCommitScope_ACU` 用 `options.chatKey ?? currentChatKey`，于是永远与当前聊天一致。
- 已排除：
  - `verifyCommittedCatchUpReplay` 失败会先返回 `integrity_failed` 并 `reloadStorageProvider`，这条路径不写终态；但验证在切换前已完成、或切换发生在验证之后与 `refreshData` 之间的成功路径，不检查聊天身份，仍会进入终态写入。
  - `executionSnapshotContextStillMatches_ACU` 的检查点在循环开始前（`4567`、`4582`），循环中与终态前没有再次检查。
  - `persistCatchUpTerminalProgress('stopped')` 也可能由 `abortOnChatMutation` 中止触发（切聊天会 abort catch-up 的 controller），因此切聊天不仅影响成功终态，也影响 stopped/failed 终态。
- 测试：`source/tests/service/table/update-orchestrator.test.ts` 的追平用例只断言终态写入的参数（`workingDataMode:'none'`、`targetMessageIndex`、`strictSave:true`），没有用例把 `getChatArray_ACU`/`currentChatFileIdentifier_ACU` 在终态前换掉；`mockRunTableWriteTransaction` 也绕过了真实作用域校验。
- 把握程度说明：缺一步端到端探针——需要在 `verifyCommittedCatchUpReplay` 之后、`persistCatchUpTerminalProgress` 之前切聊天，并让新聊天的 delayed rebuild 已把 `currentJsonTableData_ACU` 载入，观察是否真的落到新聊天。代码路径已经读穿，但具体切换时点能否满足这两个条件未实测，故标「待坐实」；`chatKey` 缺省导致作用域检查恒通过这一点是确定的。
- 修法方向：run 开始时捕获 chatKey，`persistCatchUpTerminalProgress` 透传给 `runTableUpdateCommit_ACU`；终态写入前再执行一次 `executionSnapshotContextStillMatches_ACU`，不一致就跳过写入并返回 `blocked/stopped`（不把旧计划的进度写进新聊天）。
- 与以前复审的关系：新问题；与 G12-02（确认框后复核聊天）是同一类 TOCTOU，但发生在追平收尾的写入点，G12-02 的修复没有覆盖这里。

### D03-03 [P0｜待坐实（需真机）｜B｜I2] 删除当前聊天后，收尾补存只按 chatId 判断归属、严格存盘完全不检查，可能把已删除的聊天文件重新写出来

- 位置：
  - `source/src/data/gateways/chat-gateway.ts:89-98`（chatId 取值；拿不到 id 时返回 null）
  - `source/src/data/gateways/chat-gateway.ts:119-127`（`keepChatSaveDirtyIfSameChat_ACU`：id 相同或为 null 都视为“同一聊天”，继续补存）
  - `source/src/data/gateways/chat-gateway.ts:177-188`（120 秒兜底定时器也走同一判定）
  - `source/src/data/gateways/chat-gateway.ts:200-203`、`229-244`（`endChatSaveCoalescing_ACU` → `forceFlushChatSave_ACU`）
  - `source/src/data/gateways/chat-gateway.ts:307-344`（`saveChatToHostStrict_ACU` 不做删除/存在性检查）
  - `source/src/service/table/update-orchestrator.ts:5130-5133`（追平 finally 的 `endChatSaveCoalescing_ACU`）
  - `source/src/service/table/update-orchestrator.ts:6117-6124`（手动填表/重填 finally 的 `endChatSaveCoalescing_ACU`）
  - 其它 strict 写点：`source/src/service/chat/chat-service.ts:2803`（模板临时根）、`2875`（清理）、`2968`（回滚）；`source/src/service/table/update-orchestrator.ts:4756`（追平终态）
  - `source/src/presentation/bootstrap/init.ts:823-836`（`CHAT_DELETED` 只安排 5 秒后的向量清理，不中止填表、不清存盘合并状态、不标记聊天已删除）
- 触发：一键追平（或分批手动重填）已经提交了若干 bucket，存盘合并窗口里还有待存改动；用户在聊天管理里删除当前打开的聊天。
- 现象（两种事件顺序）：
  - 顺序 1（宿主先发 `CHAT_CHANGED` 或同步切换）：`currentChatSaveKey_ACU()` 变成新聊天，`keepChatSaveDirtyIfSameChat_ACU` 判为不同聊天，脏改动作废；bucket 提交的 `chatKey` 检查也会拒绝旧聊天结果。这条不会把已删除的旧文件写回（代价是这几批要重填，属 2.7 已知取舍）；但回滚/终态进度仍可能按当前聊天执行（见 D03-01、D03-02）。
  - 顺序 2（宿主只发 `CHAT_DELETED`，或 `CHAT_CHANGED` 晚于我们的 finally）：当前 chatId 仍指向被删除的聊天（或者删除后 `getCurrentChatId()` 返回空，按 `119-127` 仍算“同一聊天”），`endChatSaveCoalescing_ACU` 的收尾补存会调用宿主 `saveChat()`；`saveChat()` 只能存当前聊天，于是把聊天数组里仍然存在的旧内容重新写成已删除的文件。120 秒兜底定时器（`177-188`）在长追平运行中也可能更早触发同一条路径。回滚的 `saveChatToHostStrict_ACU`（`chat-service.ts:2968`）和追平终态严格存盘（`update-orchestrator.ts:4756`）同样没有删除检查。

- 原因（关键代码）：

## 设计层面的疑虑（不计入缺陷）

- **清理是持久化副作用，回滚句柄却只存在内存里**：`clearManualRefillSheetDataInRange_ACU` 用 `saveChatToHostStrict_ACU` 把清理立即落盘，回滚完全依赖 orchestrator 局部变量里的 handle。切聊天、应用被杀或编排器异常退出时，旧聊天的清理没有可恢复的持久化证据。R3-06 只解决了“同一聊天内零提交回滚”的双根问题；按 chatKey + 消息指纹持久化一份回滚日志，才能关闭整类问题。D03-01 是这个设计的直接后果。
- **存盘合并窗口与用户提示脱节**：设计取舍允许“切聊天丢未补存批次”，但 UI 仍用内存里的 `committedBucketCount` 说“保留了”。建议统一由编排层给出 `savedToDiskCount` / `chatChanged`，不要在 UI 猜测。
- **全局 `isAutoUpdatingCard` 没有聊天维度**：旧轮在切聊天后继续持有该标志，新聊天的自动填表会被前置检查静默跳过。即使请求被 abort，回滚/重载/刷新仍可能持续数秒；建议在 CHAT_CHANGED 时给新聊天一个“旧轮未收尾”的等待/重试，而不是一次跳过。
- **追平计划是冻结的物理下标**：一波结束到下一波开始之间的 `loadAllChatMessages_ACU` 是异步窗口，期间删楼/插楼不会重新规划；每波新捕获的 `targetGuard` 会把位移后的楼层当成“当前楼层”，只靠 persist 的目标检查兜底。概率低于“AI 在途删楼”（后者有 target watch），但多波追平 + 中间删楼仍可能留下一个未填楼层/内部空洞。C 的换聊天由每 bucket 的 chatKey 检查兜底，问题主要在 A。
