## 发现

### D02-01 [P0｜已坐实｜C｜I1] 自动填表没有 run 级聊天身份：新开聊天后，旧计划的后续组/批会把结果写进新聊天

- 位置：
  - `source/src/service/table/update-scheduler.ts:372-414`（逐组循环；失败只记 `failedGroupKeys`，不停止后续组）
  - `source/src/service/table/update-scheduler.ts:381-386`（把旧 `group.indices` 原样交给 `processUpdates`）
  - `source/src/service/table/update-orchestrator.ts:3985`（`chatHistory = getChatArray_ACU()` 只取一次引用；宿主切聊天会复用同一个数组对象，见 2.3）
  - `source/src/service/table/update-orchestrator.ts:4000-4002`（计划里的旧下标直接变成 `finalSaveTargetIndex`）
  - `source/src/service/table/update-orchestrator.ts:4042-4047`（用同一数组切片作为新聊天的上下文）
  - `source/src/service/table/update-orchestrator.ts:3381`、`615-620`（`executeCardUpdateCore_ACU` 每组开始时重新 `captureFillExecutionScope_ACU`，`chatKey`/`targetGuard` 都取**当前**聊天）
  - `source/src/service/table/table-fill-target-guard.ts:77-82`（目标下标超出捕获时长度时直接返回 `true`）
  - `source/src/service/table/storage-frame-v2-persist.ts:2249-2257`（落盘只要求目标下标在当前聊天里是 AI 楼）
- 触发：自动填表计划有 **2 个及以上分组**（例如两张表设置了不同 `groupId`/`updateConfig`，或跨 full checkpoint 的 staging 组被拆开；默认 `maxConcurrentGroups=1` 时也是顺序执行多个组）。在 group_a 的 AI 请求在途（几十秒）时，用户对同一角色卡点「开始新聊天」：
  1. 宿主派发 `CHAT_CHANGED`，`init.ts:546` 的 `abortOnChatMutation_ACU()` 中止 group_a 正在进行的 AI 请求；
  2. group_a 的 `processUpdatesBatch` 返回失败/aborted，`executeAutoUpdatePlan_ACU` 只把它记入 `failedGroupKeys`，**继续执行 group_b**；
  3. group_b 的 `processUpdatesBatch` 重新读 `getChatArray_ACU()`，拿到的还是同一个数组对象（内容已是新聊天），但 `indices` 是旧聊天计划里的下标；
  4. group_b 的 `executeCardUpdateCore_ACU` 在切聊天之后才 `captureFillExecutionScope_ACU`，`chatKey` 已经是新聊天，提交阶段的 `assertExpectedCommitScope_ACU`（`table-update-commit.ts:313-323`）和当前值一致，不会拒绝；
  5. 目标下标在捕获时可能还不存在（新聊天刚开始），`table-fill-target-guard.ts:81` 直接放行；等新聊天在该下标生成 AI 回复后，`findTargetAiMessage_ACU` 认为它是合法的 AI 楼；
  6. 旧轮生成的表格增量被写进新聊天的这条回复，并由本组收尾的 `endChatSaveCoalescing_ACU` 真实存盘。
- 现象：新聊天里的 AI 回复被写入旧轮/旧计划的填表结果（提示词上下文还可能是新聊天的空/半截内容），新聊天的表格数据被污染；旧轮还持有全局 `isAutoUpdatingCard_ACU`，新聊天自己的自动填表被压住，只能等旧轮结束，旧轮结束后还可能因 D02-04 的回声记录被跳过。
- 原因（关键代码）：

  ```ts

  const liveChat = getChatArray_ACU() || [];
  ```

- 已排除：
  - `assertExpectedCommitScope_ACU`（`table-update-commit.ts:313-323`）只比较**本批开始时**捕获的 `chatKey`；group_b 在切聊天之后才捕获，比较必然通过。
  - `table-fill-target-watch.ts` 只在 `collectGroupFillResponse_ACU`（`update-orchestrator.ts:1486`）登记**已在途**的 AI 请求；尚未开始的 group_b 没有 watch，CHAT_CHANGED 的 `abortAllActiveRequests_ACU` 也中止不了它。

### D02-02 [P1｜待坐实（需真机）｜B｜I2] 删除当前聊天没有任何填表/存盘失效处理：收尾补存可能把已删除的聊天重新写出来

- 位置：
  - `source/src/presentation/bootstrap/init.ts:825-836`（`CHAT_DELETED` / `GROUP_CHAT_DELETED` 只接到向量清理，5 秒后执行；不中止填表、不清存盘合并状态）
  - `source/src/service/table/update-orchestrator.ts:4102-4104`（每组结束 `endChatSaveCoalescing_ACU()`）
  - `source/src/data/gateways/chat-gateway.ts:194-203`（`endChatSaveCoalescing_ACU` 在窗口归零时无条件 `forceFlushChatSave_ACU`）
  - `source/src/data/gateways/chat-gateway.ts:229-244`（`forceFlushChatSave_ACU` 只按 `chatSaveDirtyChatKey_ACU` 与当前 `getCurrentChatId()` 比较）
  - `source/src/data/gateways/chat-gateway.ts:109-127`（`markChatSaveDirty_ACU` / `keepChatSaveDirtyIfSameChat_ACU` 只认聊天 id，不认聊天是否还存在）
- 触发：自动填表正在运行，用户在聊天管理里删除**当前打开的聊天**，不先关闭聊天。考虑两种宿主事件顺序：
  1. **宿主只发 `CHAT_DELETED`，过一段时间才打开别的聊天/新建聊天**：`currentChatFileIdentifier_ACU` 和 `getCurrentChatId()` 仍指向被删聊天；填表的在途 AI 请求不走 `CHAT_CHANGED` 的 `abortOnChatMutation_ACU`，会继续返回；提交层的 `chatKey` 与当前 id 仍一致，照常写入内存中的被删聊天；组结束的 `endChatSaveCoalescing_ACU` 发现 dirty 的聊天 id 仍等于当前 id，调用宿主 `saveChat()`。按 2.3 的宿主事实，`saveChat()` 只能存当前聊天，此时当前 id 指向刚被删的文件，可能把它重新写出来。
  2. **宿主先 `CHAT_DELETED`、随后立刻 `CHAT_CHANGED` 打开新聊天**：`keepChatSaveDirtyIfSameChat_ACU` 会作废旧聊天的待存改动（这一步是对的）；但 `executeAutoUpdatePlan_ACU` 不中止后续组，后续组又在**新聊天**上重新捕获身份并执行，进入 D02-01 的跨聊天写入。
- 现象：被删除的聊天文件在聊天列表里“复活”（情况 1）；或新聊天收到旧轮结果（情况 2）。此外 `executeAutoUpdatePlan_ACU:451-454` 在删除后仍会 `loadAllChatMessages` / `refreshData` / `purgeOldLayerData`，这些收尾会对当前（可能是新）聊天执行。
- 原因（关键代码）：
  ```ts
  // chat-gateway.ts:200-203
  export async function endChatSaveCoalescing_ACU(): Promise<void> {
      if (chatSaveCoalesceDepth_ACU > 0) chatSaveCoalesceDepth_ACU -= 1;
      if (chatSaveCoalesceDepth_ACU === 0) await forceFlushChatSave_ACU();
  }
  // chat-gateway.ts:120-126 —— 只比较聊天 id，删除不会改变 id
  function keepChatSaveDirtyIfSameChat_ACU(scene: string): boolean {
      if (chatSaveDirtyChatKey_ACU === null) return true;
      const key = currentChatSaveKey_ACU();
      if (key === null || key === chatSaveDirtyChatKey_ACU) return true;
      ...
  }
  ```
- 已排除：
  - `init.ts:834-836` 的 `CHAT_DELETED` handler 只调用 `cleanupSummaryVectorIndexForDeletedChat_ACU`（5 秒延迟），不做填表/存盘失效。
  - `runTableUpdateCommit_ACU` 的 `assertExpectedCommitScope_ACU` 只比较 `currentChatFileIdentifier_ACU`；删除聊天不会改变这个值（宿主是否会在删除时同步更新 id 取决于实现，标待真机）。
  - `forceFlushChatSave_ACU` 没有任何“当前聊天文件是否还存在”的探测；`chatSaveDirtyChatKey_ACU` 的 null 分支还会在宿主不暴露 id 时一律按同一聊天处理。
  - `purgeOldLayerData_ACU` 虽有 `guardChatSwitch: true`，但那只是按聊天 id 复核，不阻止删除后的收尾。
- 测试：
  - `tests/data/gateways/chat-save-coalescer.test.ts:225` 有「记下改动后已切到别的聊天 → 冲洗时作废」，只覆盖切换，不覆盖删除；删除后 id 不变的情况完全没有用例。
  - `tests/presentation/bootstrap/init.test.ts:364-377` 只断言 `CHAT_DELETED` handler 已注册，没验证删除后填表/存盘行为。
  - `checkpoint-delete-guard.test.ts` 覆盖的是被删楼层的 checkpoint 前移，不覆盖聊天文件删除。
- 修法方向：在 `CHAT_DELETED`/`GROUP_CHAT_DELETED` 上登记“该聊天已删除”，立即作废该聊天 id 的 coalescer dirty，并让填表 run 在下一个批次/提交前检查并中止；`forceFlushChatSave_ACU` 在调用 `saveChat()` 前应确认当前聊天仍存在（宿主能提供存在性探测时），或至少不要为已删除的聊天 id 补存。删除当前聊天时也应把在途填表视为目标失效。
- 与以前复审的关系：新问题；B 场景在第二轮没有专门条目（G05-04 是删楼守卫，不是删聊天）。

### D02-03 [P2｜已坐实（机制）/待坐实（错位落地）｜A｜I3] 删楼后尚未开始的后续组/批不重新校验计划下标：目标守卫在删楼后才拍快照，挡不住位移

- 位置：
  - `source/src/service/table/update-scheduler.ts:381-386`（旧 `indices` 原样下传）
  - `source/src/service/table/update-orchestrator.ts:3985`、`4000-4002`、`4042-4047`、`4074-4086`（批次下标、上下文、保存目标都来自计划/复用数组）

  - `source/src/service/table/table-fill-target-guard.ts:72-82`（只禁止“捕获后同一下标换成另一条回复”，不禁止“计划下标在捕获前已经位移”）
  - `source/src/presentation/bootstrap/init.ts:1290-1310`（`MESSAGE_DELETED` 只 `cancelPendingAutoTasks` + 中止目标已失效的在途请求；不通知已开始的自动填表 run 作废计划）
- 触发：自动填表有多组或多批。group_a（或 batch 1）的 AI 请求在途时，用户删除一条位于 **group_a 目标之后、但位于 group_b（或 batch 2）目标之前** 的楼层（包括删除“后续组的目标楼”本身；如果删的是当前组的最后一楼，则后续组的目标直接越界，结果是整轮失败而不是错写）。`abortTableFillRequestsWithStaleTarget_ACU` 只检查当前已登记的在途请求：group_a 的目标没变，不会被中止，正常提交；随后 group_b/batch 2 开始，用旧 `indices`：
  - 如果位移后的目标下标落在一个 AI 楼（连续 AI 楼、narrator 旁白等），`captureFillExecutionScope_ACU` 在删楼后重新拍守卫，守卫看到的是“删楼后的聊天”，不会判 stale，提交层也会接受——旧结果被写到一条并非计划目标的楼层；
  - 如果落在 user 楼或越界，`persist` 返回 `no AI message found`，或 `autoUpdateTokenThreshold` 把批次 `continue` 掉，整轮失败/静默漏填，但已提交的前置组保留。
- 现象：目标楼层被填错/漏填，表格与剩余楼层不一致；用户看到内部错误（“没有找到 AI 消息”类）或没有任何提示。已提交的前置批次不会回滚（按设计保留），所以是“半截”状态。
- 原因（关键代码）：
  ```ts

  const lastMessageIndexOfBatch = batchIndices[batchIndices.length - 1];

  // update-orchestrator.ts:620 —— 删楼之后才捕获守卫
  const targetGuard = captureTableFillTargetGuard_ACU(liveChat, () => getChatArray_ACU() || []);
  ```
- 已排除：
  - `abortTableFillRequestsWithStaleTarget_ACU`（`init.ts:1294`）只遍历 `activeWatches_ACU`，watch 在 `collectGroupFillResponse_ACU`（`update-orchestrator.ts:1486`）登记；尚未开始或已完成 AI 请求的组/批没有 watch。
  - `cancelPendingAutoTasks_ACU` 只清防抖定时器、递增事件代次；`processUpdatesBatch` 没有读这个代次。
  - `assertExpectedCommitScope_ACU` 的 targetGuard 是本批开始时捕获的，删楼发生在捕获之前，比较的是“删楼后的同一楼”，不会判 stale。
  - 计划层没有保存每个目标楼的 message_id / 消息对象快照，无法在后续批次重新绑定。
- 测试：

## 设计层面的疑虑（不计入缺陷）

1. **自动填表的“上下文层数”设置语义已经和 UI 脱节。** 见 D02-07。§5.6 只决定“填表范围=完整缺口”，但 UI/模板里的「上下文层数」仍被宣传为提示词窗口；如果这是有意废弃，建议把 UI 文案和字段一起收掉，避免用户以为设置生效。
2. **按 messageId 判重对“删楼重生成/滑动”依赖宿主 message_id 是否复用。** `auto-fill-echo-guard.ts` 明确不比内容（v9.1.10 的设计），如果 TT 的 `message_id` 是按楼层下标分配的（删楼后同一下标会复用），那么删除最新楼并重新生成后，新回复会被当成“旧楼回声”跳过一次自动填表；如果 message_id 是稳定唯一 id 则不会。仓库没有宿主源码，无法在 jsdom 里坐实；建议真机确认 TT 2.4.0 的 `message_id` 生成规则。若会复用，修法是登记时同时存目标楼的 `swipe_id`/`gen_started`/对象指纹，或在 `MESSAGE_DELETED`/`MESSAGE_SWIPED` 时清掉该楼记录。
3. **`autoUpdateTokenThreshold`（正文最小长度）与回声登记的组合。** 批次因正文过短被 `continue` 跳过时，整组仍可能返回成功并登记该楼“已自动填表”；如果紧接着用户滑动/重生成出长回复，这一楼会被回声判重挡一次。按现有设计这只会延后到下一次生成，影响有限，列出供复核者决定是否算 P3。
