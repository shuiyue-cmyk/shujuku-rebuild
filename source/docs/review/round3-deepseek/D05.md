- 已排除：查过 `abortOnChatMutation_ACU`、`abortAllActiveRequests_ACU`、`abortTableFillRequestsWithStaleTarget_ACU`、`cancelPendingAutoTasks_ACU` 的全部调用点——删聊天不会触发其中任何一个；`chat-gateway` 的 strict/coalesced 两个存盘入口都不做「聊天仍存在」检查；`storage-frame-v2-persist` 的 2789/3142/3146 只比较数组引用、宿主聊天 id 和目标楼对象，删除整聊天时旧数组与旧 id 都不变（或 id 在宿主内部已变但 `currentChatFileIdentifier_ACU` 滞后），挡不住。

### D05-02 [P1｜已坐实（代码/探针）；宿主时序待真机｜B｜I2/I5] 存盘合并的补存只看宿主当前聊天 id：删除当前聊天时 `replaceCurrentChat` 的空数组窗口会把被删聊天以空文件写回

- 测试：`tests/data/gateways/chat-save-coalescer.test.ts` 只覆盖「切到另一个 chat id」和「页面隐藏补存」，没有覆盖「宿主先清空数组、后换 id」的删除流程；`tests/presentation/bootstrap/init.test.ts` 只验证了页面隐藏补存的接线。
- 修法方向：在记录脏改动时同时捕获聊天身份快照（至少 `chat[0]` 的消息对象引用；可为 `null`），补存前要求该对象仍在当前 `chat` 中；或直接订阅 CHAT_DELETED，命中已删除聊天时清脏并跳过保存。窗口内若宿主切换期间的数组为空/首楼变化，一律作废而不是保存。
- 与以前复审的关系：新问题（26e453e6 引入存盘合并窗口；以前每批立即存盘，删聊后再发生的补存不存在）。

### D05-03 [P1（若 TT 不暴露 getCurrentChatId 则为 P0）｜待坐实（需真机）｜B/C｜I1/I6] 宿主读不到聊天 id（回退 `this_chid`）时合并补存分不清聊天：切到另一个已存在聊天、其楼层尚未载入时补存，会把该聊天整个覆盖成空

- 已排除：如果 `getCurrentChatId()` 可用，切到 B 后 id 会变，`keepChatSaveDirtyIfSameChat_ACU` 会作废旧脏标记（既有测试覆盖）；`chat-history.ts` 的 `getActiveChatStorageIdentity_ACU` 也有 `'__host_without_chat_id__'` 兜底，但它只用于持久化身份，不参与合并补存。宿主异常/旧版本是否真的缺 `getCurrentChatId()` 需真机确认；本机无法证明 TT 2.4.0 一定暴露它。

## 设计层面的疑虑（不计入缺陷）

- 存盘合并用「宿主可读的聊天 id」作为唯一归属凭据，本质上信任了宿主在任意过渡态都能给出稳定 id；TT 复用 chat 数组、先清后填的流程与这个假设天然冲突。建议把「是否存在未落盘改动」与「这些改动属于哪段聊天」拆开：后者用 `chat[0]` 消息对象 + `getCurrentChatId()` 双证据。
- 120s 兜底定时器只按「上次真存盘时间」计时，宿主自己的保存（用户发消息等）不会更新这个时钟，也不会触发保管库捕获；合并窗口内用户发消息时，宿主保存虽然把内存改动带上了盘，插件仍会在 120s 后重复整份保存，且删楼守卫仍认为这些产物未捕获。
- strict 存盘的「页面卸载」检测只看 window/pagehide，宿主保存队列的完成与真实落盘之间没有可观测的确认；大聊天 + 宿主队列时，strict 的「成功后做不可逆副作用」仍然建立在「宿主 resolve 即落盘」的假设上。

## 查过但判定没问题的场景

- **删楼后目标楼被换/删除**：`runTableUpdateCommit` 的 `targetGuard` 在提交前/持久化前两次检查，`persistTableMutationLogV2Core` 2790-2795 再比对目标消息对象；已覆盖（既有 `table-update-commit.test.ts` 与 `storage-frame-v2-persist.test.ts:5635-5670`）。
- **填表批的聊天切换**：显式传 `chatKey` 的 fill/collect 路径在迁移后、apply 前、持久化前都会复核；batch 路径还在 3142-3151 逐个目标楼与根楼复核消息身份（G04-01 的修复）。D05-05 只影响未传 `chatKey` 的入口。
- **正常切聊天时的合并脏标记**：id 变化会触发 `keepChatSaveDirtyIfSameChat_ACU` 作废旧脏（既有测试 `chat-save-coalescer.test.ts:224-234` 覆盖了 id 可用时的作废路径）；这是文档化的取舍（窗口内的批次重填），不算缺陷。
- **coalesced 存盘失败**：`saveChatToHostCoalesced_ACU` 在窗口外会抛给调用方，persist 回滚内存帧；窗口内只记脏，失败由后续冲洗点重试（探针/既有测试均通过）。脏标记不会把失败伪装成成功。
- **strict 存盘先于不可逆副作用（回滚对/导入/终态）**：`persistTableMutationLogV2Core` 2816 的分支正确；`saveChatToHostStrict_ACU` 的 pagehide 卸载检测也在。只有合并分支的「saved 但在内存」被向量/世界书调用方误用（见跨组线索 3）。
- **回放 evidence 复用**：`validateV2ReplayEvidenceFresh_ACU` 同时比对数组引用、isolationKey、`headRevisionDigest`、模板结构指纹和 options 指纹，聊天内容变化会失效；只有 in-flight 去重缺内容身份（D05-07）。
- **目标楼层在回放期间被删（前面楼层）**：单写路径 2793 与 batch 路径 3146-3151 会因对象身份不符拒绝；batch 路径还额外比对根楼（G04-01）。
- **12 小时/长时间运行的锁与定时器**：`chatSaveDeferTimer` 在 flush 时清理，`startCoalescedRealChatSave` 的 in-flight promise 在 finally 清空；没有发现泄漏的定时器（旧的 120s 定时器命中已切换聊天时只清脏不保存）。
- **`this_chid` 回退在正常唯一聊天场景**：同一角色只开一个聊天时 id 不变，合并不受影响；问题只在切到同角色另一个聊天且宿主读不到 id 时（D05-03）。
